# EffiSkill：挖掘“优化技能”提升代码效率优化成功率：对照实验证明了什么、没有证明什么

*Reel 解读：[arXiv 2603.27850v1](https://arxiv.org/abs/2603.27850v1)（HarnessRSI Daily 评分 67，★★）。作者：Zimu Wang、Yuling Shi、Mengfan Li、Zijun Liu、Jie M. Zhang、Chengcheng Wan、Xiaodong Gu。论文没有给出代码仓库；它声明数据与产物位于 https://doi.org/10.5281/zenodo.19249527。*

## 系统改变了自己的什么

EffiSkill 不改模型权重，测试时也不改自己。它**离线一次性构建技能库**，之后反复使用。技能库包含 29 个**算子技能**（具体的慢到快变换，例如“完整 DP 改为滚动状态”）和一小组**元技能**（负责诊断、检索、组合算子的流程）。论文没有给出元技能的数量。

**第一阶段（挖掘）。** 对成对的慢/快解法，gpt-5.1 为每一对写出结构化轨迹（ProblemBrief、SlowAudit、FastAudit、DeltaSummary）。轨迹被压缩为签名，在 TF-IDF 加 all-MiniLM-L6-v2 的混合空间中聚类，每个簇被提炼成一张技能卡；相似的卡片会合并（TF-IDF 余弦阈值 0.8，再由 LLM 合并）。挖掘语料为 900 对 Python 和 900 对 C++，只保留加速比不低于 2 的配对。论文称检查过挖掘语料与 EffiBench-X 任务没有重叠，但没有说明检查方法。

**第二阶段（推理，“无执行”）。** 对未见过的程序，系统先诊断可能的瓶颈，检索 3 组候选算子技能，由元技能为每组组合出 2 到 3 个方案，再按方案生成候选代码。这个循环内候选代码从不被执行。技能库本身没有“保留/拒绝”规则：第一阶段结束后即固定。（另有一个对所有方法一视同仁的筛选步骤：保留通过公开测试——每题 20% 的测试——的候选，并按公开测试运行时间排序。）

## 论文报告的主要结果

EffiBench-X，623 道任务，输入程序为专家标准解，每个方法每题生成 k = 8 个候选，所有方法使用相同骨干模型，每个单元格只报告一个数值（论文没有描述重复生成或多个随机种子；为降低运行时噪声，每个候选执行 3 次取平均）。OPT@k 指至少有一个前 k 候选通过全部私有测试且比输入程序快至少 10% 的任务占比。表 1，OPT@8（%），EffiSkill 对比**该列最高的基线**：

| 设置 | EffiSkill | 最强基线 |
|---|---|---|
| GPT-5-mini，Python | 37.40 | 32.42（FasterPy） |
| GPT-5-mini，C++ | 66.77 | 54.74（CoT） |
| Qwen3-Coder-30B，Python | 36.60 | 28.25（FasterPy） |
| Qwen3-Coder-30B，C++ | 56.50 | 43.98（SBLLM） |

四种设置下 EffiSkill 的 OPT@1 和 OPT@8 都是最高。OPT@1 相对最强基线的差距较小：5.29‡（GPT Python）、3.69（GPT C++）、5.30‡（Qwen Python）、5.78‡（Qwen C++）。摘要中的“3.69 到 12.52 个点”是这八个差距的最小值和最大值，与表格一致。

## 决定收益是否可信的对照实验

- **显著性。** 对每个设置中最好的非 EffiSkill 基线做单侧配对 bootstrap（对 623 道任务重采样）：八个单元格中七个 p < 0.05；GPT-5-mini C++ OPT@1（44.62 对 40.93）只有 p < 0.10。bootstrap 只对任务重采样；论文没有描述重复生成或多个随机种子，也没有报告任何方法的运行间方差；论文也未提及对八次检验的校正。一道任务相当于 0.16‡ 个点。
- **消融（表 2；该表没有标注语言，但其完整系统行与表 1 的 Python 单元格相同，因此我们按 Python 理解；每格一个数值，无标准差）。** GPT-5-mini OPT@1 / OPT@8：完整 26.48 / 37.40；去掉检索 12.20 / 27.45；用库中随机技能 13.80 / 27.82；每组只用单个方案 18.78 / 25.84。Qwen3-Coder：完整 21.35 / 36.60；去掉检索 7.22 / 9.15；随机技能 12.36 / 13.80；单方案 11.88 / 14.29。检索*相关*技能和多方案都有作用，论文的结论是“Together, these components account for the gains”（这些组件合起来带来了收益）。这些行还显示：六个消融行的 OPT@8 全都低于最朴素的 **Instruction** 基线（GPT-5-mini 为 31.62，Qwen 为 24.40）。只有“去掉检索”完全不用技能（直接由诊断摘要生成）；另外两行仍然使用技能，而 Qwen 的几行（9.15 到 14.29，对比 24.40）看起来更像是被削弱的流程，而不是能干净归因于技能库。论文没有说明 3 组技能、每组 2 到 3 个方案如何得到 8 个候选，所以无法核实单方案一行的候选集是否可比。论文把“诊断”列为组件，却没有“去掉诊断”的行，也没有元技能消融，更没有非挖掘（例如手写）技能的对照，所以“从慢/快对中挖掘”相对于“随便给一些优化提示”的价值并没有被单独隔离。随机技能一行取自同一个挖掘出的技能库。
- **预算。** 所有方法都是 k = 8 个候选。论文没有报告任何方法每题的 token、LLM 调用次数或耗时，也没有第一阶段成本（1,800 对的 gpt-5.1 轨迹、聚类、合并）。流程分为几个阶段（诊断、方案组合、生成），论文没有说明各阶段的 LLM 调用次数，因此就我们能核实的而言，预算只在候选数上对齐。
- **基线得到了什么。** 论文没有描述任何基线拿到挖掘出的技能库或 gpt-5.1 轨迹。RAG 从 PIE 检索配对，FasterPy 从“历史代码变换”检索摘要；论文没有说明它们是否使用与 900 + 900 对相同的数据（Python 的挖掘语料还包含 Mercury、Code Contests 和 APPS）。SBLLM 按论文所述是“不含基于执行的选择”的单次迭代变体，采用它是“for fair comparison”（为公平比较）；我们认为它是削弱后的改写版（我们的判断）。它的数字波动很大：Qwen、Python、OPT@8 为 8.67，Qwen、C++ 为 43.98。微调基线 EffiCoder 只出现在 Qwen 上，且从未成为最强；论文没有说明它是作者自己微调的还是使用已发布的检查点，也没有说明训练数据。基线的调参预算和采样设置均未报告。
- **留出。** 挖掘所用题目与评测任务是不同题目，论文声明做过重叠检查；两者都来自竞赛编程，作者承认“some distributional similarity may remain”（可能仍有一定分布相似性）。骨干模型或 gpt-5.1 的数据污染没有讨论。设计常数（合并阈值 0.8、3 组技能、2 到 3 个方案、k = 8）如何选定，论文也没有说明。
- **“跨语言迁移”。** RQ3 问 EffiSkill 在“从 Python 迁移到 C++”后是否仍然有效，其回答框称 EffiSkill 在“at the framework level”（框架层面）上“generalizes across Python and C++”。挖掘语料中除 900 对 Python 外还有 900 对 C++，所以这不是 Python 挖掘出的技能的零样本迁移。论文只报告了一个 29 个技能的库，没有说明该库是跨语言合并的还是按语言分别构建的。

## 收益缺失或偏小之处

- **OPT@1 的提升不大**（比最强基线高 3.69 到 5.78‡ 个点），且有一个单元格只有 p < 0.10。较大的差距（12.03 和 12.52）都是 C++ 上的 OPT@8；Python 上 OPT@8 的差距为 4.98 和 8.35。
- **仍有很大空间。** EffiSkill 在 Python 上的 OPT@8 为 37.40 和 36.60，因此 k = 8 时仍有 62.60‡ 和 63.40‡ 个百分点的 Python 任务没有合格候选。
- **正文与表格不一致。** 引言把 Qwen 的差距写成 12.36（C++）和 8.67（Python），RQ3 的回答框写“up to +12.36”；而表 1 和第 5.3 节给出的是 12.52 和 8.35（OPT@8，分别对 SBLLM 和 FasterPy）；Qwen3-Coder 的任何基线行、任何指标的差距都不是 12.36 或 8.67。我们采用表格数值。
- **任务级比较（图 5）。** 论文称 EffiSkill 在“最强的非 EffiSkill 基线”上赢的任务多于输的：对 SBLLM 为 455 / 26 / 142（胜 / 平 / 负，共 623 道‡，从图中读出），对 EffiCoder 为 401 / 41 / 181，对 CoT 为 348 / 34 / 241，对 Instruction 为 313 / 103 / 207。只有 CoT 那一格对应表 1 的领先者；另外三格的对手（SBLLM、EffiCoder、Instruction）并不是表 1 中 OPT@k 最高的基线（分别是 FasterPy、FasterPy 或 CoT、SBLLM）。论文没有定义图 5 中的“最强”，因此“收益分布广泛”这一说法并没有针对表 1 的领先基线检验过。
- **技能使用集中在一个家族。** 表 3：“实现与常数因子”一族占候选—技能对的 54.2%；代数/闭式化 19.7%；DP/状态压缩 13.1%；组合数学与数论 9.5%；图/数据结构 3.5%。论文说占比较小的数论一族“与更大的平均收益相关”，但没有给出数字；论文还说代数和 DP 两族也频繁出现，表明技能库“not limited to local cleanups”（不限于局部清理）。
- **只有一个示例。** chmax-rush! 案例中提示基线候选耗时 3838.11 ms，EffiSkill 为 1434.23 ms（2.68×）；论文称它是“a representative success case”（有代表性的成功案例），并说它“not intended to demonstrate the largest absolute gain”（并非用来展示最大的绝对提升）。

## 我们的看法

HarnessRSI 评分 **67**，★★ 档，证据等级 **retained**：被保留的产物（挖掘出的技能库）在未用于构建它的任务上被评估，论文没有展示它改进了自己的改进器。论文**报告了**：留出评测及挖掘语料与基准的重叠检查声明；去掉或随机化检索技能的消融（表 2，按 Python 理解）；对任务的配对 bootstrap；所有方法相同的候选数。论文**没有报告**：运行间方差（生成随机种子）、token/LLM 调用次数或挖掘成本、“去掉诊断”或“非挖掘技能”的对照、骨干模型的数据污染检查（而非挖掘语料与基准的重叠检查，后者已报告）。判断备注：我们的记录把 `retained_ablation` 标为 unclear，但表 2 确实去掉或随机化了检索到的技能（按 Python 理解，每格一个数值）。总体应理解为：在一个基准、两个骨干上有一致的优势，在 C++ 的 OPT@8 上最明显，推理成本未报告。
