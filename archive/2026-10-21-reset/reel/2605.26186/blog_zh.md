# SetupX：复用环境修复经验有效，但失败记忆的增益小于完整系统的领先幅度

*Reel 解读：[arXiv 2605.26186v2](https://arxiv.org/abs/2605.26186v2)，完整标题为 **SetupX: Can LLM Agents Learn from Past Failures in Functionality-Correct Code Repository Setup?** HarnessRSI Daily 评分 **64**，档位 **★★**。代码：[OpenDataBox/SetupX](https://github.com/OpenDataBox/SetupX)。*

## 系统改变了自己的什么

SetupX 留存的是**可复用的环境修复经验库**，不是更新后的模型权重。每个经验单元（XPU）包含诊断信号与适用条件、自然语言根因建议、可执行原子操作，以及命中／成功／失败遥测。来源是包含命令与错误日志的配置轨迹，以及可获得时的检察官—法官裁决。蒸馏器甚至会从最终被判 guilty 的运行中提取问题—修复对：这既不是失败任务的原样转储，也不是只收录整次成功运行的技能库。

“失败”信号分多个层次。循环内验证器判断测试错误来自环境配置还是仓库自身缺陷。最终检察官独立检查依赖、文档声明的命令和测试，法官再用针对性命令核实指控。任何指控成立，或者运行超时，都判失败。表 4 还将缺失评测数据计为失败，但未标出哪些单元格属于这种情况，也未披露其频次或分布。因此，叉号不一定代表已完成的负面功能裁决。涉及可选依赖或外部因素的指控可以被驳回。这里的独立性是**同一骨干模型上的角色分离**，不是单仓库结果另有人工真值审计。

## 迭代回路与保留／拒绝规则

1. 将轨迹蒸馏为泛化后的 XPU。向量预筛选与 LLM 共同判断语义重复；确认重复则合并信号和建议，其余候选入库。论文没有规定新经验必须先通过留出集性能门槛才能入库。
2. 根据当前情境与原始错误输出检索候选，并加入历史效用信号；LLM 从十个候选中最多选出三个。
3. 为 Docker 容器建立快照，把建议适配为当前仓库的修复命令，执行并比较前后错误状态。试用成功则保留改动，否则恢复快照；智能体也可退回多个更早的快照。这个局部环境门槛，不是 XPU 入库门槛。
4. 下次检索时，回看上次检索锚点之后最多五步：建议被采纳且问题解决或改善，记成功；被采纳但问题持续或恶化，记失败；是否采纳或贡献不明，记中性。这些结果改变遥测与未来排名，不会自动删除失败条目。
5. 配置提示词要求先成功执行循环内 VERIFY 才能 FINISH；随后由独立角色的检察官—法官审计给出最终评测裁决。

遥测分层阈值 a = 0.2、b = 0.1 根据当前 XPU 遥测选取，以使各层大致平衡。**论文没有说明使用哪个独立训练／开发划分来选择这些默认值、检索设置，也没有说明基线调参的划分。**

## 论文报告的主要结果

主实验使用 **100 个经筛选的 Python 仓库**：从 EnvBench 的 329 个仓库中，先筛选测试资产，再做预实验划分难度后抽样；各仓库固定版本。所有对比系统使用 **qwen3.5-plus**、全新的 **ubuntu:22.04** 容器、每次运行 **3600 秒**全局超时，以及相同的最终检察官—法官裁决（§6.2）。

| 单仓库通过率 | 论文结果 |
|---|---:|
| SetupX + XPU | 92% |
| 去掉 XPU 的 SetupX | 82% |
| 最强 CLI 基线 Claude Code | 73%‡ |
| 最强专用工具 ExecutionAgent（ExecAgent） | 59%‡ |

论文报告相对 Claude Code 领先 **19 个百分点**，相对 ExecAgent 领先 **33 个百分点**。但隔离留存经验库贡献的比较是 **92% 对 82%**，即论文明确给出的 **10 个百分点**增益。完整系统领先的其余部分，不能全部归功于失败记忆。

这些是跨仓库的通过比例，**不是重复运行的均值**。结论明确说当前评测侧重单次容器化配置；主比较与检索消融都没有种子方差、置信区间或重复评测的选择协议。相同时间上限并不等于 token、重试次数或整个生命周期的经验采集算力匹配。

## 决定收益是否可信的对照

- **做了同仓库排除，但不是不相关分布测试。** 干净知识库有 600 条建议，来源于 EnvBench Python 仓库池。评测前删除了与 100 个目标仓库对应的条目（§6.2、附录 G）。论文报告了这一身份级排除，但没有报告 fork／近重复／仓库家族泄漏审计，也没有说明评测目标之间是否冻结或重置在线遥测与新经验。描述的规则并不排除共享依赖或相关仓库，实际重叠程度没有量化。
- **检索质量很重要（图 6b）。** 干净知识库加 LLM 筛选为 92%‡，直接向量检索为 86%‡；加入合成噪声后，筛选为 88%‡，直接检索为 81%‡，而无 XPU 是 82%。论文报告重排序在干净库和噪声库分别带来 6 和 7 个百分点。这个没有方差的合成噪声压力测试，不能证明实际失败记忆都能自行纠错。
- **逐项说明基线获得什么。** Claude Code、OpenCode、Qwen Code 分别获得相同的模型、容器、超时和最终裁决器；ExecAgent、Repo2Run、EnvBench 也各自获得这些共同条件。论文没有报告给其中任何基线配置可比的 XPU 库或失败记忆增强。Repo2Run 本身确有命令级自适应回滚，SetupX 则提供智能体控制的多步快照回滚。去掉 XPU 的 SetupX 是直接的经验库移除对照。未见单独隔离回滚或遥测的消融，也未报告同等记忆基线、等重试预算比较或基线调参预算。
- **更强模型在这里没有更高得分。** Selector + Clean 配置换成 Claude Opus 4.6 仍为 92%，API 成本报告为超过十倍（§6.4）。这只是此基准上的一个对应配置，不是普遍模型排名。绝对 API 成本、供体轨迹生成、蒸馏、嵌入、延迟审计与快照开销都没有逐项核算，积累失败库的成本仍未量化。
- **多仓库是补充证据。** 在 22 个家族上，两者都在 **17/22** 达到至少 Mostly。SetupX 为 **6 Full / 11 Mostly**，Qwen 为 **1 Full / 16 Mostly**（表 2）。三名评估者独立检查容器，再讨论达成共识；这不是单仓库的检察官—法官协议。优势在 Full—Mostly 边界，不在“至少 Mostly”的总体比例。不过，表 2（p17）与附录 E（p18）报告：Qwen 的 MISP 运行遇到端口 80 被前一家族遗留的 Saleor 进程／容器占用。因此跨家族服务隔离并不完善；论文未报告清理后的修正重跑。MISP 两者均为 Partial，这并不能证明干净重跑会改变任何一方的汇总结果。

## 收益缺失或不均匀之处

经验库的增量在**中等难度**最明显：有 XPU 为 89%‡，无 XPU 为 69%‡。低难度接近天花板，为 100%‡ 对 95%‡；高难度为 79%‡ 对 72%‡（图 5a）。所以不能简单概括成“记忆增益都由最难仓库贡献”。论文强调工具链／测试／文档领域，在 20 个仓库上 SetupX 零失败、最强 CLI 基线五次失败；剩余 SetupX 失败主要在 AI/ML 和 DevOps。这仍是单个筛选过的 Python 基准，不是广泛、重复的迁移研究。

表 4 也有逐仓库反向结果：**trax、neuralforecast、ajenti、civet** 在无 XPU 时通过、加 XPU 后失败。这是观测结果，不是对两次运行为何分歧的因果诊断。Claude Code 在 trax、neuralforecast、civet、iree-llvm-sandbox、qiita 上通过，而 SetupX + XPU 失败；总体更好不等于逐仓库全面领先。

多仓库轨道中，**robotframework** 的 SetupX 为 Mostly，Qwen 为 Full；**label-studio** 为 Shallow 对 Partial；**flyte、bitcart** 为 Partial 对 Mostly；**MISP** 两者均为 Partial。表格中 SetupX 低于 Mostly 的成员是 label-studio、flyte、MISP、bitcart、frappe/erpnext，但附录 E 后续文字将其称为“four Partial/Shallow cases”。这一措辞无法与各行及已印出的汇总对应。我们使用表 2，保留该差异为未解决，不推测原因。

## 我们的解读（Our read）

HarnessRSI 评分 **64**，档位 **★★**，证据等级 **retained**（本地最新判断：b17 批次）。最有支持的结论是：在有用的验证—修复框架之上，**检索留存经验能帮助配置已排除自身条目的仓库**。经验库移除以及检索／噪声对照支持这一解读。

论文报告了仓库身份级排除、共同超时、留存经验库消融，以及补充性的人工多仓库评估；没有报告重复运行方差、匹配的总算力、给竞争智能体配备可比失败库、经验采集成本、相关仓库泄漏审计，或单独验证遥测驱动的改进器长期进步的实验。这支持“留存经验有用”，尚不是成本核算完整、持续自我改进的学习机制证据。
