# H01 — Curate a Living Memory with Edit Operations
_parent: **Abstract Experience into Reusable Guidance** (`abstract_experience_into_guidance`) · corpus support: 24 papers (accepted 9 · rejected 2 · unlabeled 13)_

## Tactical pattern
The guidance store is a living document maintained by explicit edit operations — add, update, merge, delete,
no-op, link, or a localized delta — chosen by an LLM curator after each interaction or batch. Consolidation,
conflict resolution, and forgetting are first-class steps, so the store stays compact and consistent instead of
growing monotonically, and incremental delta edits avoid the context collapse that comes from rewriting the whole
store as one summary. The decisive design choice is the editing policy over existing entries: what triggers an
edit (a correctness judgment, a verifier, a retention-strength threshold, an uncertainty signal), what scope it
may touch (one entry, its neighbors, its retrieval hooks), and what is protected from deletion. Success is
certified by downstream gains at a bounded store size, with an ablation of the edit operations themselves.

## Step-by-Step
1. Define the store's unit and its edit vocabulary (add / update / merge / delete / no-op, or delta patches) and
   make each edit an explicit, logged decision rather than a free rewrite of the whole context.
2. Gate every edit on an outcome signal — correctness judgment, verification, expert guidance, or a retention
   threshold — and state that signal's reliability; curators driven by imperfect model judgments propagate errors
   into the persistent store.
3. Make consolidation and forgetting explicit: merge near-duplicates, resolve conflicts with timestamps or
   precedence, decay or drop low-utility entries, and revise retrieval features as well as entry content.
4. Prefer localized deltas over monolithic rewrites, and show the store neither collapses (losing detail) nor
   bloats (redundant for simple tasks) as interactions accumulate.
5. Ablate the curator, not just the store, and separate the construction stream from evaluation. Both rejected
   members frame the editable store as a replacement for weight updates, which sets the bar at weight-based
   optimizers.

## Differentiation within parent
H01's move is the maintenance policy over a single memory's existing entries. H00 concentrates on how a new lesson
is extracted from outcomes and mostly appends it. H02 formats knowledge as portable, versioned skill packages
mined from many sources and published to a shared library, rather than editing one agent's working memory in place.

## When to pick this one
The tell: the store already works but degrades with scale — repeated rewriting drops useful detail, contradictory
or stale entries accumulate, or the full history no longer fits. Pick H00 instead while the lesson set is still
small and extraction quality is the bottleneck; pick H02 when the artifact must travel across agents or users.

## Tactical failure mode
The signature failure is treating the editable store as the optimization substrate itself — searching over
natural-language updates with graders and rubrics, or evolving applicability conditions of library entries — and
claiming it replaces weight updates, while the mechanism leans on grader-driven state-space search, so the edit
policy and the extra search compute are entangled. Accepted members' own limits name the weaker spots shared
by the cluster: edits driven by imperfect model judgments, knowledge that remains benchmark-specific, repeated passes over the same
benchmark that complicate any unseen-instance reading, and online adaptation on test samples. The root assumption
that fails is that a well-maintained store is automatically a better learner; the edit policy's contribution has
to be isolated.

## Lessons
### From accepted work
- Treat forgetting as a feature: retention thresholds and consolidation keep the store usable as histories grow.
- Choosing add / update / delete / no-op per salient fact keeps a persistent context consistent across sessions.
- Localized delta edits preserve earlier strategies while adding lessons, avoiding the collapse of monolithic
  rewriting.
- New entries can trigger revisions to related older entries and their links, so the store is not frozen after
  insertion.
- Revise retrieval hooks as well as content; an entry that is right but retrieved at the wrong time is a failure.
### From rejected work
- Calling a partitioned, grader-refined knowledge base an optimizer invites a comparison against real optimizers
  and budgets that must be supplied.
- Evolving an entry's applicability conditions is a retrieval fix; show it outperforms simply retrieving better.
