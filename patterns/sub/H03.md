# H03 — Retrieve and Adapt Precedent Cases
_parent: **Index Raw Experience for Reuse** (`index_experience_for_reuse`) · corpus support: 44 papers (accepted 9 · rejected 9 · unlabeled 26)_

## Tactical pattern
Store solved episodes as near-raw cases — whole trajectories, induced workflows, subtask solutions, or
failure-to-fix repair records — and, for each new task, retrieve the closest precedents by similarity,
category filter, or distribution matching, adapt them to the new arguments, act, and append the outcome so
the case base grows with use. The decisive design choice is the *unit and cleanliness of a case*: stripping
instance-specific values, or cutting episodes into functional subtasks, is what lets precedents compose
instead of merely resembling the new task. A second decisive choice is the *write gate*: only cases that
pass an executable check, validation run, or outcome gate enter the store. Success is certified by
removing or freezing the retained case base and showing the gain disappears, ideally on tasks never used
to build the store.

## Step-by-Step
1. Define the case unit. Decide whether a case is a full episode, a parameterized subtask, or a repair
   record keyed by its diagnostic trigger, and remove instance-specific values so it can be re-bound to
   new arguments; whole-episode cases match on surface similarity and retrieve precedents whose local
   reasoning differs.
2. Gate what gets written. Admit a case only after an executable test, simulation, or outcome threshold
   confirms it; stores filled from self-judged success inherit the judge's errors, and stores curated by
   hand (manual verification of every example) do not scale — the latter is a boundary rejected work crossed.
3. Make retrieval selective, not maximal. Filter by functional category or task type before similarity
   ranking and cap how many cases enter context; mixed-quality or dissimilar precedents are a recurring
   stated source of degradation.
4. Adapt, then append. Re-bind the retrieved case to the new task, execute, and append the new outcome
   (including corrected failures) with provenance, so the store's growth is auditable.
5. Separate the store's construction stream from evaluation. Build the case base on tasks disjoint from
   the test tasks, report order sensitivity, and run a retained-store ablation; headline gains from extra
   attempts or memory built on the test stream are what sink otherwise similar systems.

## Differentiation within parent
H03 keeps precedent near-raw and puts the work into matching and adaptation of individual cases. H04
changes the *shape* of the store (tiers, graphs, clusters, paging) and argues from index design rather
than from case reuse. H05 changes *when* memory is consulted (triggered, gated retrieval) rather than
what is stored. Abstraction-family patterns outside this parent compress experience into lessons; H03
members that also distill insights still lean on concrete demonstrations as the load-bearing part.

## When to pick this one
Pick H03 when tasks recur with concrete, re-bindable structure (same site, same toolchain, same repository
family, same repair class) and a cheap executable check exists to certify a case before storing it. The
tell is that a correct past solution, re-parameterized, would solve much of the new task. If recall fails
because the history is too large or tangled to search, H04 fits better; if the problem is that injected
experience distracts at steps that do not need it, H05 fits better.

## Tactical failure mode
The root assumption that fails is *"a similar-looking precedent is an applicable precedent, and the store
is independent of the test stream."* Rejected members lean on distribution-distance retrieval sensitive to
hyperparameters, on multi-pass gains that spend extra attempts, on human-guided or manually verified
exemplars, or on in-context exemplar selection and prompt-guidance databases where the "case base" is
incidental rather than a growing, gated store. Across all 44 members, 14 stated limitations concern overlap
between memory construction and the evaluation stream or task-order dependence (accepted 3 · rejected 1 ·
unlabeled 10), and 9 note that case admission or scoring relies on a model judge (accepted 3 · unlabeled 6).
Five members state that retrieved noisy or dissimilar cases degrade results (accepted 2 · unlabeled 3).

## Lessons
### From accepted work
- Removing instance-specific values from stored routines lets them compose across tasks instead of only
  matching near-duplicates.
- Segmenting an episode by functional intent and filtering by category before similarity ranking aligns
  the retrieved case with the current reasoning stage.
- Gating writes to memory with executable verification keeps unsupported patterns out as the store grows.
- Validated cross-task solutions can replace, not just warm-start, new-task search — report the cost saved.
- Showing the gain vanishes when the retained store is removed is the near-universal certificate (7 of 8).
### From rejected work
- Retrieval tuned by distance-to-task with sensitive hyperparameters, and no held-out split, did not carry.
- Gains that come from additional attempts, with an unclear construction split, read as budget, not reuse.
- Precedents that need manual verification or human-written abstraction exemplars undercut the
  "improves with use" claim.
- Selecting or synthesizing in-context exemplars per query is not by itself a growing case base.
- Five of the nine rejected members are low-fit: matching, diagnosis, opponent-modeling or exemplar schemes
  where precedent reuse is incidental to the method.
