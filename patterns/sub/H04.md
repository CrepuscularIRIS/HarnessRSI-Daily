# H04 — Restructure the Memory Substrate
_parent: **Index Raw Experience for Reuse** (`index_experience_for_reuse`) · corpus support: 33 papers (accepted 12 · rejected 7 · unlabeled 14)_

## Tactical pattern
Reorganize the persistent store into a structure built for long-horizon recall — semantic hierarchies with
child pointers, temporal or entity graphs, overlapping clusters, coarse-to-fine tiers, or OS-like paging —
and attach explicit promotion, linking, update-rate, and decay rules so retrieval stays precise and cheap
as history grows. The decisive design choice is to stop forcing one representation to serve both as
content and as index: stable abstractions hold consolidated content while separate cues, pointers, or
cluster boundaries decide what is reachable, and updates touch only the affected region instead of
rebuilding the whole store. The claim is certified by recall accuracy *and* cost (tokens, calls,
maintenance) as the history scales, against flat retrieval over the same raw material.

## Step-by-Step
1. Name the recall failure that flat storage causes — fragmented facts, conflicting cross-session
   evidence, cross-topic interference, or exhaustive-search cost — and pick the structure that targets it,
   not the most expressive one available.
2. Decouple content from index. Keep consolidated memories stable and expose retrieval through separate
   cues, child indices, or entity links, so one item can be reached by several paths without duplication.
3. Specify update dynamics. Set different update rates for fast-changing facts versus slow traits, use
   evidence thresholds before overwriting, and make insertions local so new batches do not force a global
   rebuild; generated summaries that are never verified are a stated route for hallucinations to spread.
4. Move expensive maintenance off the critical path. Batch or defer consolidation and report its token,
   call, and storage cost; unoptimized graph maintenance overhead is a limitation a rejected member left open.
5. Certify with structure ablations at scale. Compare against flat retrieval on the same raw material,
   ablate the structural component, and report seed variance and held-out separation — the items this
   sub-pattern most often leaves unclear.

## Differentiation within parent
H04 is about the shape of the store and its index. H03 keeps a flat-ish case base and invests in matching
and adapting individual precedents; H05 keeps the store but changes when and whether it is consulted.
Abstraction-family patterns outside this parent decide *what lesson* is written; H04 members may abstract
too, but their argument rests on representation and index design, not on the lesson text.

## When to pick this one
Pick H04 when the history is long-lived and growing (multi-session dialogue, persistent user state,
large document streams, multi-agent team traces) and the bottleneck is that relevant items become hard or
expensive to reach, or that new evidence conflicts with old. The tell is that retrieval quality degrades
with store size even though the needed information is present. If tasks recur and a re-bound past solution
would suffice, H03 is simpler; if the store is fine but is injected at the wrong moments, use H05.

## Tactical failure mode
The root assumption that fails is *"a better-shaped store yields better recall by itself."* Rejected
members propose plausible structures — sentence-level graphs, stored intermediate answers, offline chunk
covering, native key-value-cache memory, dual-level procedural memory, evolving schemas, active profile
upkeep — and one rejected profile-plus-hierarchy design is close to accepted ones, so structure choice
alone does not separate outcomes; two further rejected members are low-fit chunk-selection or answer-caching
schemes rather than experience stores. Stated risks across members:
generated or summarized memories propagating hallucinations (2 members: accepted 1 · rejected 1), indexing
or maintenance cost growth (4 members: accepted 1 · rejected 1 · unlabeled 2), and excess retrieval adding
irrelevant context (2 members: accepted 1 · unlabeled 1).

## Lessons
### From accepted work
- Let memory content and its retrieval index use different representations; many-to-many cues reach
  details that a single abstraction would bury.
- Hierarchies with explicit child pointers confine search to relevant subtrees and cut retrieval cost.
- Separate update scales: evidence-thresholded slow traits versus fast facts handle cross-session conflict.
- Make updates local (affected clusters or subtrees only) and defer heavy consolidation off the online path.
- Keep a derived memory unit only if it is non-redundant, so the store deepens rather than bloats.
### From rejected work
- A store shape close to accepted designs (active profile upkeep plus hierarchical retrieval) still did not
  carry; structure choice alone does not separate outcomes.
- Generated memories inserted without verification invite hallucination propagation reviewers can point to.
- Context-compression or chunk-selection schemes framed as memory are weak fits for experience reuse.
- Leaving graph or index maintenance overhead unoptimized and unmeasured weakens a scaling claim.
- Re-representing memory as native key-value-cache blocks moves the contribution toward attention-level
  retrieval engineering and away from organizing reusable experience.
