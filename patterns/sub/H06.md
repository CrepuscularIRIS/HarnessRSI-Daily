# H06 — Discover Skills Through Self-Directed Practice
_parent: **Crystallize Solutions into Executable Capabilities** (`crystallize_executable_capability`) · corpus support: 14 papers (accepted 7 · rejected 3 · unlabeled 4)_

## Tactical pattern
Before any deployment demand exists, the agent generates its own practice tasks (or walks a pool of training
problems), writes code that solves them, executes that code to confirm it works, and abstracts each verified
solution into a parameterized function that joins a persistent library. The decisive design choice is the
admission gate: a skill enters the action space only after execution shows it succeeded, was actually used,
and changed the environment as intended — or, in the strongest variants, only if the current policy could not
already reproduce it cheaply. Later skills call earlier ones, so the library compounds. Success is certified by
performance on requests the practice phase never saw, and by ablating the retained library while holding the
rest of the agent fixed.

## Step-by-Step
1. Define the practice source: a self-proposed curriculum, a pool of training problems, or self-generated
   trajectories from first principles. Keep it disjoint from the evaluation queries; harvesting skills from the
   same tasks you later score on is what sinks the weakest member of this sub-pattern.
2. Solve each practice task with generated code and repair it against execution feedback until it runs and
   meets the task's success signal. Prefer an execution-based check over an LLM critic wherever ground truth
   exists; a critic that misjudges success silently pollutes the library.
3. Abstract the verified solution into a parameterized, documented callable. Validate the abstraction — not just
   the original instance — and deduplicate against existing entries so retrieval stays tractable.
4. Admit only what adds capability: gate on replayed success, actual invocation of the skill, and an observable
   effect, or on the policy's inability to re-derive the result. Keep rollback for edits that regress.
5. Evaluate on held-out requests with a retained-library ablation, and report the full construction cost
   (practice, generation, validation), not only the per-query inference saving. Omitting construction cost is a
   limitation explicitly recorded against a rejected member.

## Differentiation within parent
H06 grows the library proactively from an exploration curriculum before any live task asks for it. H07 forges
a tool inline when a running task exposes a gap, so its trigger is demand, not practice. H08 does not acquire
new skills at all; it restructures, repairs and promotes relations among skills that already exist.

## When to pick this one
Pick H06 when the environment is cheap and safe to explore, recurring sub-procedures can be anticipated, and an
execution signal can tell a working skill from a broken one. The tell is a domain where many future requests
share low-level procedures (application control, web interaction, proof steps) and you can afford an offline
practice budget. If gaps are idiosyncratic and only visible mid-task, H07 fits better; if a library already
exists but is flat, redundant or brittle, move to H08.

## Tactical failure mode
The signature failure is a library whose growth is not separated from its evaluation: skills are harvested from
the very tasks used to measure reuse, held-out separation is absent, and no leakage guard is reported, so gains
cannot be distinguished from memorized task solutions. A second failure shifts the "skill" from executable code
to learned control policies with generated rewards or evolved symbolic interpretations; the other two rejected
members are low-fit to the pattern in this way, and one reports simulated-only evaluation with
user-configured parameter ranges. The root assumption that fails is that a skill which worked once in practice is a reusable capability
— without verification of the abstraction and out-of-practice evaluation, it is only a cached trajectory.

## Evidence profile
Counted over the 8 corpus (arXiv full-text) members carrying an `evidence` block (7 accepted, 1 rejected):
- Held-out separation: yes in 4, partial in 1, no in 2, unclear in 1. All 4 "yes" are accepted; the rejected
  member reports no.
- Cross-task transfer: yes in 3, no in 2, unclear in 3.
- Retained-artifact ablation: yes in 5 (4 accepted, 1 rejected) — the most common strength.
- Variance: never reported as yes (unclear 7, no 1). Budget matching: unclear in all 8.
- Optimizer/construction cost: yes in 1. Improver comparison: unclear in all 8.
- Leakage guard: never present (none 1, untested 2, unclear 5). Code released: yes in 2.
Typical report: held-out success plus a library ablation. Typical omission: variance, budget-matched baselines,
and any guard against practice/evaluation overlap.
Rejected members are mostly abstract-only OpenReview records, so evidence and limitations are not comparable across outcomes.

## Lessons
### From accepted work
- Gate admission on replayed execution — task success, real use of the skill, and an observable state change —
  so the action space only grows with artifacts that demonstrably work.
- Admit a new primitive only when the current policy cannot cheaply re-derive it; this keeps the library
  compact and makes each entry a genuine capability increment.
- Treat retained functions as optimizable parameters with rollback on regression, and check that training-set
  gains survive on a held-out split.
- Let a strong model build skills once and a cheaper model invoke them; the amortization argument is clean
  when held-out queries confirm the transfer.
- Pair held-out evaluation with a retained-library ablation; together they carry most of the evidential weight.
### From rejected work
- Harvesting tools from the evaluation tasks themselves, with no leakage guard, leaves reuse claims
  uninterpretable.
- Reporting inference savings while excluding the cost of building the library invites a cost objection.
- Small evaluation samples on secondary benchmarks weaken an otherwise broad generalization claim.
- Recasting skills as trained parameterized policies with generated rewards drifts away from verifiable
  executable artifacts and loses the pattern's main advantage.
- Simulated-only evaluation with user-configured parameter ranges reads as a narrow demonstration rather than
  open-ended skill discovery.
