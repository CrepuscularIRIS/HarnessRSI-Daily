# H07 — Forge Tools When a Capability Gap Appears
_parent: **Crystallize Solutions into Executable Capabilities** (`crystallize_executable_capability`) · corpus support: 22 papers (accepted 8 · rejected 7 · unlabeled 7)_

## Tactical pattern
While solving a live task, the agent recognizes that nothing in its inventory covers a need, and then searches
for, generates, installs or wraps code — including existing external repositories or reference material — into a
callable tool, debugs it against execution feedback, and registers it for later reuse. The decisive design choice
is the repair loop that turns a first draft into a working tool: separating abstract tool creation from concrete
invocation, feeding execution tracebacks back into fixes, capturing environment setup so the tool is reproducible,
or grounding generation in external references when the model's own knowledge is insufficient. Success is
certified when forged tools are reused on later tasks and an ablation shows the retained tools, not just the
backbone, carry the gain.

## Step-by-Step
1. Make gap detection explicit: a decision point (decompose the need, check retrieval, decide whether to answer
   directly, reuse, or forge) rather than forging on every step, which adds noise and latency.
2. Ground the new tool in something verifiable — an existing repository, API documentation, reference text or
   demonstrations — instead of relying solely on what the model already knows.
3. Build and repair in a sandboxed, reproducible environment: snapshot installation steps, run, read the
   traceback, fix, rerun. Execution without errors is not semantic correctness; validate on examples with known
   answers.
4. Register the tool with a description and usage examples, and atomize or organize it so later retrieval
   selects it precisely.
5. Evaluate reuse on tasks that did not produce the tool and ablate the retained inventory. Evaluating reuse on
   the source benchmark that generated the tools is the recorded weakness of a rejected member; keep the forged
   tool as the measured contribution rather than one component inside a broader framework.

## Differentiation within parent
H07 is demand-triggered: the gap appears inside a running task and tool creation is an inline decision. H06
practices proactively and builds its library before demand exists. H08 neither practices nor forges; it
reorganizes, repairs and promotes skills already in a library.

## When to pick this one
Pick H07 when needs are long-tailed and unpredictable (specialized scientific computations, unfamiliar packages,
repository-backed functionality) so a practice curriculum cannot anticipate them, and when an execution sandbox
can check a candidate. The tell is that the missing capability already exists somewhere as code or documentation
and only needs wrapping and repair. If recurring procedures can be practiced cheaply offline, H06 is stronger; if
the inventory is already large and redundant, H08 is the right move.

## Tactical failure mode
The signature failure is folding tool forging into a larger architecture — a hierarchical memory, a multi-agent
coordination scheme, a planner over workflows, or a trained arbitration policy — so that the forged
tool is no longer the isolated, measured contribution and no repair loop is singled out. Four of the seven
rejected members take this shape. A second variant measures reuse on the same distribution that generated the
tools and leans on small sampled benchmarks. The root assumption that fails is that runtime tool creation is
self-evidently valuable; without held-out reuse and a retained-tool ablation, reviewers cannot separate a growing
inventory from a capable backbone.

## Evidence profile
Counted over the 8 corpus (arXiv full-text) members carrying an `evidence` block (7 accepted, 1 rejected):
- Held-out separation: never yes (unclear 6, no 2).
- Cross-task transfer: yes in 1. Variance: yes in 1. Budget matching: unclear in all 8.
- Optimizer/construction cost: yes in 1. Improver comparison: unclear in all 8.
- Retained-artifact ablation: yes in 5 (4 accepted, 1 rejected) — the dominant form of evidence.
- Leakage guard: none in 1, unclear in 7. Code: yes in 3, announced in 2.
Typical report: an ablation removing the retained tools. Typical omission: any held-out reuse split, variance and
cost accounting — which is weaker than H06's profile.
Rejected members are mostly abstract-only OpenReview records, so evidence and limitations are not comparable across outcomes.

## Lessons
### From accepted work
- Separate creating an abstract tool from invoking it on the concrete instance; it lowers reasoning burden and
  lets execution errors drive targeted rectification.
- Use execution tracebacks in a run–review–fix loop to repair wrappers around existing code, and capture
  environment setup so the result is reproducible.
- Ground generation in external references or demonstrations when the needed knowledge lies outside the model,
  and validate on worked examples.
- Pair distilled experience with the asset store so lessons from past failures steer the next creation.
- Report a retained-tool ablation; it is the evidence accepted members most consistently supply.
### From rejected work
- Evaluating tool reuse on the benchmark that produced the tools leaves generalization unestablished.
- Burying forging inside a broad memory or coordination architecture dilutes the claim and leaves no isolated test
  of the forged artifact.
- Delegating the forge-or-invoke decision to a trained policy shifts the contribution to training and away
  from the executable artifact.
- Converting human corrections into stored skills depends on a human in the loop and weakens the autonomy claim.
- Reuse that only holds across inputs sharing one fixed schema is a narrow form of capability growth.
