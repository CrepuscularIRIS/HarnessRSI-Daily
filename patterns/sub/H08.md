# H08 — Maintain a Compositional Skill Graph
_parent: **Crystallize Solutions into Executable Capabilities** (`crystallize_executable_capability`) · corpus support: 12 papers (accepted 5 · rejected 1 · unlabeled 6)_

## Tactical pattern
The executable skill library is treated as a structured program rather than an append-only list: skills are
organized as a typed graph or DAG of compositions, execution traces assign responsibility to individual skills
for localized repair, recurring text plans or tool sequences are promoted into new callable primitives once
recurrence is demonstrated, and refactoring is protected by maturity gating and rollback. The decisive design
choice is what evidence licenses a structural edit — trace-level fault localization, observed recurrence, or
verified compilation of a workflow — rather than semantic similarity alone. Success is certified when edits
improve or preserve task success, mature skills survive refactoring, and promoted primitives are actually reused.

## Step-by-Step
1. Represent skills with explicit typed interfaces and composition edges, so retrieval can follow structure
   (prerequisites, call relations) instead of flat text similarity.
2. Trace each execution down to the skills it invoked and propagate responsibility, so a failure is repaired
   where it occurs rather than by rewriting the whole library.
3. Promote only on evidence: compile a workflow or tool sequence into a primitive after it has recurred and been
   verified, and keep one-off experience as flexible text.
4. Refactor and consolidate with execution-based validation and rollback. Checking preservation by an agent
   review instead of by execution is the shape of the sole rejected member; a refactor gate validated on very few
   tasks with a loose tolerance is a recorded weakness even among accepted ones.
5. Report variance and cost alongside utility, and guard against negative transfer (contrastive utility,
   suppression of skills that hurt) so that the graph's growth is shown to help rather than merely accumulate.

## Differentiation within parent
H08 operates on relations among existing executable skills — composition, promotion, repair, consolidation — not
on acquiring new ones. H06 acquires skills proactively through practice; H07 forges them inline when a live task
exposes a gap. H08 is the natural follow-on once either sibling has produced a library large enough to become
redundant, brittle or hard to retrieve from.

## When to pick this one
Pick H08 when the library already exists and its pain points are structural: retrieval overload from many
near-duplicate tools, skills that cannot branch on state, faults that cannot be localized, or site- or
instance-specific skills that fail to transfer. The tell is that adding more skills no longer helps. If the
bottleneck is still missing capabilities, use H06 (anticipated, practicable) or H07 (unanticipated, on demand).

## Tactical failure mode
The signature failure is restructuring without execution-grounded validation: clustering tools by semantic
similarity and refactoring shared logic, then relying on a reviewing agent to judge that functionality was
preserved. The single rejected member follows this shape; with n = 1 it is a hypothesis, not a finding. Other
members also record the boundary: trace consistency does not guarantee online correctness, specification filters
assume faithful LLM judgments, and rollback gates validated on few tasks can let regressions through. The root
assumption that fails is that a well-organized library is a better library; structure only pays when each edit
is checked by execution against the skills it touches.

## Lessons
### From accepted work
- Propagate responsibility through execution traces so repairs stay local, and gate refactors on skill maturity
  with rollback to protect what already works.
- Encode state-dependent control logic inside skills (branching, variable binding) and graft recovery behavior
  from successful recovery trajectories.
- Compile verified workflows into skills and score them with contrastive utility to suppress negative transfer.
- Wait for recurring solution patterns before abstracting a tool; speculative tool invention produces weak,
  rarely reused abstractions.
- Decouple a skill's abstract goal from its concrete implementation so one objective can bind to several
  environments and transfer.
### From rejected work
- Consolidating generated tools by semantic clustering, with preservation checked only by a reviewing agent,
  leaves functional equivalence unverified (single rejected member; tentative).
- Framing the contribution as reduced retrieval ambiguity without an execution-level test that refactored tools
  still solve their original tasks leaves the central claim unsupported.
