# H09 — Propagate Feedback Through a Compound System
_parent: **Attribute Failures and Patch the Incumbent** (`attribute_and_patch_incumbent`) · corpus support: 12 papers (accepted 5 · rejected 3 · unlabeled 4)_

## Tactical pattern
Treat the deployed system as an executed graph of prompts, tools, code and, optionally, collaboration
topology. Run it, attach rich feedback (a critique, a verifier diagnostic, a failing test) to the final
output, and route a component-specific critique to each upstream node, conditioned on what that node
received from its neighbors; then update the implicated nodes jointly and discard or roll back updates
that are illegal or regress. The decisive design choice is the *scope* of propagation: a full backward
chain, the minimal execution subgraph that actually produced the output, or local refinement with
bounded forward nudges. Members show that deep global chains grow and lose specificity, so the scope
choice is load-bearing. Success is certified by the end-to-end task score of the jointly updated graph
on inputs separate from those that generated the critiques, ideally with the optimizer's extra model
calls reported, since they grow with the number of graph edges.

## Step-by-Step
1. **Make the graph explicit.** Record which node produced which intermediate so that output feedback
   can be tied to the minimal subgraph responsible, not to the whole workflow.
2. **Pick feedback that localizes.** Prefer verifier diagnostics or first-failure localization over a
   single global critique, and route by failure type (instruction edit vs. tool repair vs. structure edit).
3. **Bound the propagation.** Limit depth or refine locally before nudging neighbors; refining only the
   per-node gradient formula on a fixed topology, with no argument that it improves performance, is the
   shape that sinks the rejected members.
4. **Gate every update.** Retry or discard illegal edits, roll back regressions, and validate structural
   proposals before adoption; budget for this, because proposal validation is expensive.
5. **Certify cleanly.** Keep a held-out split apart from the critique set, report optimizer cost, do not
   rest the claim on auto-generated proxy tests or model-generated evaluation alone, and make baselines
   reproducible; failing to reproduce baselines is a limitation a rejected member had to concede.

## Differentiation within parent
H09 is the only sibling that splits credit across several *interacting* components and updates them
jointly. H10 rewrites a single textual artifact from its own critique; H11 edits reusable skill files with
section-level attribution; H12 also localizes across modules, but by a coding agent reading harness source
and traces, not by propagating critiques along a graph. When the graph's shape itself is the object of
search rather than its node contents, the neighboring pattern is topology search (H17, H18).

## When to pick this one
The tell: several model calls or tools whose errors interact, rich feedback at the output, and genuine
ambiguity about which node is at fault. If one component dominates the errors, H10 is cheaper. If the
components are executable code with inspectable source, H12's code-level diagnosis is more direct. If
failures cluster inside reusable procedures invoked across tasks, use H11.

## Tactical failure mode
The root assumption is that an LLM critic reasons accurately about each component's contribution to the
output. Members' own limitations name it: dependence on the LLM reasoning correctly about the optimized
components, no guarantee that semantic gradients improve performance, and (in the rejected knowledge-store
editor) an assumption that expert feedback isolates errors caused by the edited store. When it fails, credit
is misassigned, updates drift, and cost scales with edges. A second failure is certification by proxy:
automatically generated proxy tests and model-generated evaluation stand in for ground truth.

## Lessons
### From accepted work
- Use the execution trace's minimal subgraph to connect output feedback to heterogeneous upstream parameters.
- Treat prompts, tools and pipeline structure as jointly learnable, with rollback for illegal updates.
- In deep graphs, local critic-driven refinement plus bounded nudges beats long global backward chains.
- Making topology editable per task widens the search, but it then leans on proxy tests; certify beyond them.
- Attribution itself can be supervised, e.g. from counterfactual replay and injected faults.
### From rejected work
- A sharper per-node gradient on a fixed topology, without an improvement argument, read as incremental.
- Editing an external knowledge store assumes the feedback isolates store-caused errors; check that first.
- The edit space over a large store needed tree search; scope the decomposition before searching it.
- Porting the propagation loop unchanged to a single pipeline domain reads as an application.
