# H11 — Revise Skills by Failure Attribution
_parent: **Attribute Failures and Patch the Incumbent** (`attribute_and_patch_incumbent`) · corpus support: 14 papers (accepted 2 · rejected 0 · unlabeled 12)_

## Tactical pattern
Keep a library of reusable skill documents (instructions, often with attached code) and improve it by
attributing execution failures to a specific skill file or section. The decisive design choice is the
attribution gate: separate genuine skill defects from execution lapses, so that a failed run does not
trigger a rewrite of guidance that was actually correct (lapses can be routed to a reminder rather than
an edit). Edits are bounded (textual edit budgets, diagnosis-bound repair principles, contrastive patches
tied to a trace), re-run on the attributed cases, and retained only if measured utility improves on a
validation set that is disjoint from the data used to select the edit. Certification is held-out task
success of the agent using the revised skill, ideally across models or harnesses, since the skill is
meant to be portable.

## Step-by-Step
1. **Batch and attribute.** Map recurring failures to specific skill sections across many runs rather than
   rewriting from a single trajectory.
2. **Split defect from lapse.** Edit the skill only when the skill is wrong; coarse trajectory-based rewriting
   corrupts valid guidance when the failure was an execution lapse.
3. **Bound the edit.** Apply an edit budget and keep a trace-linked edit history so that consolidation does
   not erase working guidance or let the skill drift.
4. **Re-run and retain on evidence.** Replay the attributed cases, then keep the revision only if it improves
   (or does not degrade) a validation set selected disjointly from the edit data.
5. **Keep the test set closed.** Do not inspect test performance across revision stages, do not overfit visible
   verifier checks, and report held-out tests rather than optimization rollouts.

## Differentiation within parent
H11 is specialized to reusable skill documents with per-section attribution and an explicit defect-vs-lapse
distinction. H10 rewrites a prompt or rule document without that distinction; H09 splits credit across a
graph of interacting components; H12 patches executable harness code. Outside the parent, library
governance (H30) decides which skills are admitted or retired, while H11 edits their content.

## When to pick this one
The tell: an agent repeatedly invokes the same procedural guidance across tasks, and failures cluster around
particular procedures. Pick H11 when you can tell "the skill is wrong" from "the agent did not follow it". If
the guidance is a single task prompt, H10 suffices; if the failure is in tool dispatch or control flow, use
H12; if the question is whether a skill should exist at all, use admission/retirement (H30).

## Tactical failure mode
The root assumption is that LLM attribution of an execution failure to a skill section is correct. Unlabeled
members name the consequences: dependence on correct attribution, knowledge failures that plateau after the
initial refinement, conflicting historical references, overfitting to visible verifier checks, and gains that
are optimization rollouts rather than held-out tests. Evaluation is often tiny (e.g. only eight test tasks per
skill, or only eight hard adaptation tasks) and the suites are synthetic, so task and rubric quality decide
validity. Textual guidance also cannot supply capabilities beyond what the frozen agent can follow.

## Lessons
### From accepted work
- Package improvements as portable skill folders rather than model-specific monolithic prompts.
- Retain a proposal only when it improves a validation-ranked frontier, not when it merely looks sound.
- Cluster execution traces before proposing a mutation, so one repair serves a whole failure family.
- Gate on non-degradation of a validation set, and ablate the retained skill to show it carries the gain.
- Concede the open transfer question (cross-model, cross-harness) rather than claim it.
### From rejected work
- No rejected member exists in this bundle (0 of 14). Risks below come from unlabeled members' limitations.
- Inspecting test performance across revision stages turns the test set into a selection set.
- Visible verifier checks can be overfit; keep a hidden check.
- Compute for repair is rarely budget matched against simply re-running the agent more.
- Reported transfer was restricted to cases the source already solved; test transfer on failures.
