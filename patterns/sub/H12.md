# H12 — Patch the Harness from Trace Diagnosis
_parent: **Attribute Failures and Patch the Incumbent** (`attribute_and_patch_incumbent`) · corpus support: 36 papers (accepted 3 · rejected 4 · unlabeled 29)_

## Tactical pattern
Treat the agent harness (tools, middleware, memory, control flow, prompts as files) as a versioned codebase.
A coding agent reads execution traces together with harness source, localizes a *recurring* failure
mechanism to editable code, writes a scoped patch with a falsifiable prediction of what it should fix, and
promotes it only after replay or regression checks, rolling back on failure. The decisive design choice is
what evidence the proposer sees and how edits are scoped: raw traces, code and scores across all prior
candidates beat fixed summaries; task-agnostic edit constraints and separately scoped module tracks beat
unrestricted joint rewrites, which overfit and interfere. Success is certified by improvement on tasks that
were not used to propose or promote the patch, with proposer token cost counted in the budget.

## Step-by-Step
1. **Expose raw evidence.** Give the proposer selective access to full traces, code and scores of prior
   candidates instead of compressed feedback; budget for histories that can reach millions of tokens.
2. **Diagnose mechanisms, not instances.** Generalize instance-specific fixes into reusable changes; contrast
   successes with failures on the same task, and aggregate across tasks before editing.
3. **Scope and predict.** Constrain edits to a module and attach a falsifiable expectation, so the next round's
   outcomes can confirm or reject the patch and interfering edits can be traced.
4. **Promote on a separate split.** Replay failures, check regressions, roll back otherwise; a held-out split
   that is also used for promotion, or selection on the scored batch, is no longer held out.
5. **Build a harness, not a deliverable.** The rejected members mostly evolved one domain program (a mapper,
   an RL agent, an analysis script, a game player); that reads as program synthesis, not harness improvement.

## Differentiation within parent
H12 edits executable scaffolding using code-level diagnosis. H10 and H11 edit textual guidance (a document,
a skill); H09 propagates critiques across a graph of components instead of having an agent read source.
Outside the parent, self-referential improvement (H19) additionally edits the improver itself.

## When to pick this one
The tell: failures live in routing, state, tool dispatch, memory handling or context management, where
text-only adaptation cannot reach them, and both traces and source are inspectable. If the fault is a
wording problem in one artifact, H10 is cheaper; if it sits in a reusable procedure, H11; if multiple LLM
nodes interact and no source-level fault is visible, H09.

## Tactical failure mode
The root assumption is that a patch which passes replay on the evolution tasks reflects a general mechanism.
Unlabeled members name how it breaks: all gains measured on evolution tasks, a held-out split reused for
promotion, transductive selection on the scored batch, self-attribution that misses regressions, components
that interfere, refinement that preserves cheating as a skill, and trace observability that does not prevent
reward hacking. Weak target models fall below a capability floor, and equal evaluation budgets do not mean
equal proposer cost.

## Lessons
### From accepted work
- Let the optimizer retrieve execution evidence actively, then generalize proposals into reusable scaffold changes.
- Give the proposer the full candidate history on disk rather than summaries or prescribed parents.
- For small models, abstract a few failure reflections into compact, localized patches with bounded retries.
- Report optimizer cost alongside held-out results; every accepted evidence block does.
- Concede what equal evaluation budgets hide (proposer tokens) instead of claiming cost parity.
### From rejected work
- Evolving a single domain program against its own benchmark reads as application work, not harness work.
- Contrastive repair across all failures is a good idea, but aimed at one domain's analysis code it patches a
  deliverable, not a reusable harness.
- Templates that need hand-written heuristics and docstrings move the expertise back to the human.
- Confinement to one environment or framework limits the generality claim the move needs.
