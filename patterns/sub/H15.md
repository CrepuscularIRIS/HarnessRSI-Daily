# H15 — Guide Evolution with Distilled Search Memory
_parent: **Search a Population Against an Executable Fitness** (`population_search_executable_fitness`) · corpus support: 15 papers (accepted 7 · rejected 0 · unlabeled 8)_

## Tactical pattern
The search keeps an explicit, evolving knowledge layer on top of its population: distilled transformation rules
(including reversed failed optimizations), context-conditioned edit residuals, hierarchical or graph-structured
histories that record derivation rationale, design principles and positive or negative relational rules, reusable
code skills credited by measured fitness change, or a scored queue of improvement ideas. That layer conditions the
next proposals and is rewritten as results arrive, sometimes shared across parallel agents, branches or whole
campaigns. The search learns how to search as well as finding better candidates. The decisive design choice is how a
memory item earns its place — credit by child-versus-parent fitness change, confidence gating over repeated
observations, retention of negative evidence — so that noisy feedback is not amplified. Success is certified by
beating the same search without the memory under a matched budget, ideally with transfer to a new task or campaign.

## Step-by-Step
1. **Choose a checkable unit of knowledge.** Transformations, residuals, snippets or rules that can be applied and
   then verified by the evaluator, rather than free-form notes nobody re-tests.
2. **Credit every item by evidence.** Attribute fitness deltas to the item that produced them, require repeated
   observations before trusting it, and keep negative knowledge that can veto a proposal; naive success memory
   amplifies noisy feedback, as one member's own motivation states.
3. **Bound and structure the memory.** Cap its size, organise it hierarchically or as a graph, and backtrack when
   progress stalls so a polluted local history does not trap the search.
4. **Declare and test the sharing scope.** Per task, across branches, or across campaigns — then test transfer
   explicitly; per-task memory with transfer deferred, or transfer shown on very few pairs, are recorded limitations.
5. **Ablate the memory under matched budget, with a held-out split.** Among the 6 members with an `evidence` block,
   only 1 reports a retained-artifact ablation and 4 report no held-out separation; skipping this leaves the memory's
   causal role unestablished.

## Differentiation within parent
- **vs H14:** H14 relies on the raw parent pool; H15 adds an explicit knowledge layer distilled from it.
- **vs H13:** H13 may show the proposer a score-sorted trajectory of prompts, which is undistilled history.
- **vs H16:** H16 is defined by which candidates are retained; H15 by what is learned from all of them.
  Editing the search procedure itself, rather than conditioning proposals, belongs to a different parent pattern.

## When to pick this one
Evaluations are expensive, the campaign is long, and what works has recurring structure. The tell is that the same
kind of edit keeps being rediscovered, the same failures keep recurring, or parallel workers duplicate each other. If
evaluations are cheap and runs short, plain program evolution (H14) is simpler; if the useful knowledge is mainly
which candidates complement each other on different instances, a frontier rule (H16) fits better.

## Tactical failure mode
The root assumption that fails is that what the memory stores is what caused later gains, and that feedback is
reliable enough to distil. Members' own limitations name the gaps: artifact-reuse associations that do not isolate
causal memory effects, no ablation isolating the self-evolution component, memory that is uninformative until enough
observations accumulate, inability to discover directions outside observed experience, and external leaderboard
feedback steering the search policy. A second recurring gap is budget: iteration-matched comparisons that do not
equalise tokens or wall-clock, and baselines run at different published budgets. No member in this bundle is labeled
rejected, so this failure mode is drawn from limitations and evidence gaps, not from rejection outcomes.

## Lessons
### From accepted work
- Distilling slow-to-fast transformations into a bounded memory, including reversed failures, lets search proceed
  where no expert heuristics exist yet.
- Hierarchical memory plus progress-triggered backtracking keeps parallel explorers from collapsing into one polluted
  history.
- Recording why a candidate was derived (an entailment structure) lets critics plan the next derivation instead of
  sampling fixed operators.
- Crediting reusable code skills by child-versus-parent fitness change, with a separate diagnostic critic, makes the
  memory both transferable and auditable — the only member reporting a tested leakage guard and an artifact ablation.
- Promoting only externally grounded evidence into persistent state stops runs from rebuilding the same
  infrastructure.
### From rejected work
- No member is labeled rejected; the cautions below come from limitations recorded across members.
- Correlating artifact reuse with gains is not evidence that the memory caused them; ablate it.
- Memory that trusts single successes amplifies noise; gate on repeated observations.
- Letting leaderboard or reporting feedback steer the search policy blurs selection and evaluation.
- Iteration-matched comparisons can hide large token or wall-clock differences; report both.
