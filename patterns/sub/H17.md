# H17 — Search an Offline Agent Design Space
_parent: **Search the Agent's Architecture** (`search_agent_architecture`) · corpus support: 21 papers (accepted 8 · rejected 7 · unlabeled 6)_

## Tactical pattern
The agent's structure (which modules exist, how they are wired, what workflow code runs between them) is
written down as an explicit, searchable object: executable code, a typed or acyclic graph, a set of
standardized module slots, or a probability distribution over connections. It is then optimized offline
against a task set with execution scores as fitness, via evolution, tree search or policy-gradient updates
over edges, and a single frozen design is deployed for the whole task distribution. The decisive choice is
not the search algorithm but the search-shaping primitive that makes each expensive execution count: an
archive of scored stepping stones a meta-agent can recombine, standardized interfaces plus a cheap
surrogate that filters candidates before execution, an experience tree tying each edit to its measured
effect, or a staged order (tune local prompts, prune the topology space, retune jointly). Success is
certified by the frozen design's score on held-out problems, ideally also on another task family or
executor model, together with an honest account of what the search cost.

## Step-by-Step
1. Fix the design representation before picking an optimizer, and state what it excludes (cycles, agent
   caps, node types, operator sets). Check that every statically valid design actually compiles into a
   runnable system; a space that is valid on paper but fails at realization is a recurring rejection point.
2. Split the data into a search set and an untouched evaluation set, and keep any archive or knowledge base
   built during search on the search side. Optimizing and scoring on the same small subset is the leak
   that most often undercuts a reported gain.
3. Add one search-shaping primitive that cuts wasted executions and ablate it directly. Co-evolving roles,
   operators, curriculum and control rules in one framework without isolating which axis pays is what
   sinks several rejected members.
4. Account for optimizer cost (design executions, tokens, wall-clock) and compare with hand-built and
   prompt-only baselines at matched inference budget, since extra agents raise inference cost too.
5. Certify transfer: frozen design on a held-out split, a second task family and a different executor;
   report seed variance. If component-level blame drives edits, show the blaming judge beats the plain
   end-to-end score rather than adding noise.

## Differentiation within parent
H17 yields one design per task distribution before deployment and then stops changing. H18 (Co-Evolve Roles
and Topology at Test Time) keeps rewiring the team during inference, per instance or per stream. Adjacent
parents: H27 trains a generator that emits designs instead of searching once per distribution, and H09
propagates textual feedback through a structure it does not necessarily change.

## When to pick this one
The tell: a stable task distribution with a scorable executor, where the wiring of a hand-built pipeline
(not its prompts) caps performance, and you can afford many offline executions but want zero adaptation
cost at deployment. Prefer H18 when instances differ so much that one frozen design is mismatched, or when
there is no labeled search set and feedback only arrives at test time. Prefer H27 when many distributions
will arrive and search should be amortized into a learned proposer.

## Tactical failure mode
Root assumption that fails: that a design's score on the search set is a faithful proxy for deployment
value, and that a larger or more jointly optimized design space is a contribution in itself. Rejected
members show it three ways: (a) widening the space to co-evolve everything at once (roles, collaboration
structure, mutation operators, difficulty curriculum, control rules) with no axis-level ablation;
(b) refining the representation or credit signal of an existing workflow search (type-constrained graph
edits, block-level blame) where static validity does not guarantee execution and blame rests on noisy LLM
judgments over a narrow benchmark family; (c) packaging modular pipeline infrastructure as optimization.
Unlabeled members expose the evidence gaps: optimization and evaluation reusing one small subset, fitness
on a small fixed training subset, search collapsing onto recurring strategies, dependence on a strong
initial archive, and designs whose gains hinge on the executor model they were searched with.

## Lessons
### From accepted work
- Keep an expanding archive of scored designs so a coding meta-agent recombines stepping stones instead of
  restarting from a template each round.
- Standardize module interfaces so parts of separate systems become recombinable, and put a cheap
  in-context predictor in front of costly executions to filter unpromising designs.
- Tie each structural edit to its measured execution effect in a tree of experience, so later expansions
  start from what demonstrably worked.
- Tune local prompts before searching topology, prune the topology space, then retune globally; topology
  search over untuned components measures the wrong thing.
- Changing the objective can beat more search: ranking compositions by tail risk rather than mean success,
  or predicting workflow utility from code, prompt and graph views, replaces exhaustive execution.
### From rejected work
- Co-evolving every axis at once without isolating which one carries the gain reads as a system, not a finding.
- A tighter representation or finer blame signal for an existing workflow search must show valid designs
  execute and blame beats end-to-end scores; otherwise it reads as incremental.
- Tooling that makes pipelines modular and comparable is infrastructure unless it enables a search result
  nothing else could.
- "Holistic" joint optimization of agent function and collaboration structure needs the per-dimension
  ablation that justifies going joint.
