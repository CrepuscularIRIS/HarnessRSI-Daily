# H19 — Apply the Improver to Itself
_parent: **Make the Improver Editable** (`make_the_improver_editable`) · corpus support: 14 papers (accepted 4 · rejected 1 · unlabeled 9)_

## Tactical pattern
A single lineage in which the optimizer — a mutation or system prompt, a meta-agent program, or a loop
configuration — is either run on its own source (self-application) or tuned by an outer loop that scores it by
the downstream performance of the artifacts it produces. The improved improver then replaces the incumbent and is
reused for later rounds, so task gains can compound into better proposal behavior. The decisive design choice is
what stays fixed as an anchor: the outer evolutionary algorithm, the meta-optimizer, the promotion authority, or a
review gate. Success is certified empirically, by evaluating descendants of the improved improver against those of
a fixed, hand-designed one — not by proofs.

## Step-by-Step
1. **Choose the editable improver surface and name the anchor.** Decide exactly which part proposes changes
   (mutation instructions, optimizer prompt, scaffold code) and which part is immutable (promotion rule, evaluator,
   base-model API, tool access). Leaving the boundary open — an accepted member itself reports that unrestricted
   agents can call stronger models — means gains can no longer be attributed to the improvement logic.
2. **Score the improver by its products.** Fitness for the improver is the downstream utility of what it produces
   (task prompts, programs, adaptation sessions), measured through an inner loop. Define this before any
   self-application so the improver cannot grade itself on a metric it also edits.
3. **Self-apply under a guard.** Run the improver on its own definition; retain the rewrite only if descendants
   improve. Add a recovery path for rewrites that crash or terminate optimization — self-modification can halt the
   loop, so rollback belongs in the method, not in an afterthought.
4. **Separate selection tasks from reported tasks and repeat.** Select improver rewrites on one task set and report
   on another; run more than one independent lineage. Compounding evaluation noise can falsely promote rewrites,
   and a single uncontrolled lineage cannot isolate the gain from self-application.
5. **Certify against a fixed improver.** Compare the self-improved improver to the original fixed one, report the
   extra model-call cost of the outer loop, and ablate the self-applied component.

## Differentiation within parent
H19 is single-lineage: one incumbent improver is replaced when a rewrite wins. H20 instead keeps an open-ended
archive and branches from non-best ancestors, so its load-bearing elements are archive and parent selection.
H21 does not edit the improver's own code at all; it redesigns a separate learning mechanism (memory, retrieval,
context construction) and scores it by how well the agent learns with it.

## When to pick this one
Pick H19 when the improver is a compact, cheaply evaluated artifact (a prompt or short program) whose quality
shows up directly in the score of what it produces, and when a single improving trajectory is affordable to
audit. The tell: progress stalls because the hand-written mutation or optimization instructions plateau, not
because the search lacks diversity. If runs converge to local optima or the best current agent is a poor parent,
H20 fits better; if the bottleneck is how the agent accumulates and reuses experience, pick H21.

## Tactical failure mode
The root assumption that fails is that **a rewrite that scores better on the improver's own development loop is a
better improver**. Members report the symptoms: self-modification can terminate optimization; fourteen percent of
robustness trials finish worse than initialization (reported by an accepted member); unrestricted agents can call
stronger models; evaluation for a meta-trained policy reuses its meta-training environments; an outer-improver
comparison is inconclusive because additional seeds are costly; benchmark snapshots of a single deployment
lineage do not isolate evolution gains; LLM reviewers used as the anchor can share blind spots. A second recurring
gap is that the anchor itself (outer algorithm, meta-optimizer, prompting topology) stays hand-designed, which
caps how "self-referential" the claim can be.

## Lessons
### From accepted work
- Evolve the mutation instructions together with the task prompts, so the improver is selected by the same fitness
  that selects task artifacts.
- Score an optimizer by the downstream performance of the programs it optimizes; an outer loop over optimizer
  prompts and compositions then needs no separate quality signal.
- Report robustness failures honestly (runs that end worse than initialization) alongside the headline gain.
- State openly which meta-level stays fixed; accepted members name their fixed outer algorithm or meta-optimizer
  as a limitation rather than hiding it.
- Show the outer-loop cost and a comparison to the original hand-designed improver.
### From rejected work
- Only one rejected member remains, low-fit and with no recorded limitations, so this side yields a single lesson.
- Learning a reusable cross-task template is not the same move as making the proposer editable; a low-fit rejected
  member edits a transferable task structure, which reads as prompt optimization rather than self-application.
