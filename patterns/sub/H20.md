# H20 — Branch Self-Modifying Agents from an Archive
_parent: **Make the Improver Editable** (`make_the_improver_editable`) · corpus support: 8 papers (accepted 4 · rejected 0 · unlabeled 4)_

## Tactical pattern
Self-modifying agents — usually coding agents whose own implementation is the edit target — are kept in an
open-ended archive. A parent is sampled by current performance, novelty, or an estimate of how productive its
descendants will be; it inspects and edits its own code; the offspring is evaluated and archived even when it is
not immediately better, so weak agents can serve as stepping stones to strong ones. The decisive design choice is
the parent-selection rule: who gets to modify next. Success is certified empirically by benchmarking descendants,
ideally on tasks and models not used to drive the search.

## Step-by-Step
1. **Seed with a working self-editor and a multi-objective evaluator.** Start from an agent that can already read
   and rewrite its own implementation, and score offspring on performance, time, and cost together. Short timeouts
   can amplify gains from faster tooling, so fix the timeout policy before comparing.
2. **Design parent selection as the core contribution.** Go beyond "pick the top scorer": estimate descendant
   productivity at the level of a whole subtree, sample for diversity, or select a group of parents whose
   experience traces are pooled. The highest-performing current agent need not be the best parent.
3. **Let the archive inform the edit, not only the ranking.** Use stored trajectories across tasks and lineages to
   diagnose which defect to target, so each edit consumes fewer task evaluations.
4. **Archive non-improving offspring and control evaluation cost.** Keep descendants that do not beat their parent;
   use staged screening and schedule evaluation separately from modification so cost does not explode
   (one accepted member reports about $7000 for fifteen iterations).
5. **Certify on tasks the search never saw.** Report on a held-out split and on transfer to other tasks or base
   models, with independent search seeds. Repeatedly evaluating on small fixed benchmark subsets is the gap every
   evidence-bearing member leaves at least partly open.

## Differentiation within parent
Unlike H19's single lineage, H20's load-bearing elements are the archive and the parent-selection rule: progress
may route through ancestors that were never the incumbent. Unlike H21, the evolved artifact is the self-modifying
agent itself (task code plus, in some members, the meta-agent that proposes changes), not a separate memory or
context mechanism.

## When to pick this one
Pick H20 when the improvement landscape is deceptive: immediate benchmark score poorly predicts which agents will
spawn productive descendants, single-lineage search stalls in local optima, and evaluations are reproducible
enough to compare many branches. The tell is that useful improvements require several individually unhelpful
edits. If the improver is a cheap prompt with a direct fitness signal, H19 is simpler; if the agent's weakness is
how it stores and reuses experience, H21 targets that directly.

## Tactical failure mode
The root assumption that fails is that **benchmark performance on a repeatedly reused task subset is a valid proxy
for self-improvement ability**. Members state the consequences: repeated subset evaluation risks benchmark
overfitting; optimization on benchmark tasks can overfit; matched agent counts do not establish matched monetary
cost; independent evolution seeds are limited, and two directional lineages are not independent repeated seeds.
A second assumption — that the archive makes the improver editable — fails when archive maintenance, parent
selection, and evaluation remain handcrafted, which several members list as a limitation. Theoretical optimality
links, where claimed, rest on restricted cost and repeatability assumptions or on access to the true descendant
productivity.

## Lessons
### From accepted work
- Keep offspring that are not immediately better; diversity in the archive is what lets later agents escape a
  local optimum.
- Choose parents by estimated descendant productivity rather than current score, and decouple evaluation
  scheduling from modification.
- Pool experience traces across a selected group of parents so complementary discoveries merge instead of staying
  on isolated branches.
- Score offspring on performance, time, and cost jointly, and publish the search cost.
- Show transfer of discovered agent designs to other tasks or base models (2 of 4 evidence-bearing members do).
### From rejected work
- No member is labeled rejected (0 of 8), so no rejection lesson can be drawn; the cautions below come from stated
  limitations of accepted and unlabeled members, not from outcomes.
- Reward-free variants that select successors without downstream scores still need independent search replication.
- Reported cost savings computed on subsets where all methods succeed overstate the advantage.
- Evolved agent code can become structurally complex; report its size or readability alongside the score.
