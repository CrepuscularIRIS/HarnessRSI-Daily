# H21 — Redesign the Inner Learning Mechanism
_parent: **Make the Improver Editable** (`make_the_improver_editable`) · corpus support: 8 papers (accepted 4 · rejected 0 · unlabeled 4)_

## Tactical pattern
An outer loop searches over the design of the mechanism through which the inner agent learns from experience —
memory schema, executable update and retrieval code, context-construction skills, or a pool of retrieval policies —
instead of over the task policy or the improver's own code. Each candidate design is installed, the agent
accumulates experience with it over a stream or set of tasks, and the design is scored by how well the agent
learns (task success, learning-curve gain, resource use). The decisive design choice is making the learning
mechanism an executable, swappable object whose quality is measured only through downstream learning. Success is
certified by held-out tasks and by transfer of the evolved design to new tasks, domains, or base models.

## Step-by-Step
1. **Reify the learning mechanism as code.** Express schema, write/update logic, retrieval logic, and usage
   instructions as one executable unit the outer loop can rewrite, so a design is a program rather than a set of
   hand-tuned knobs.
2. **Score by learning, not by a single episode.** Evaluate each candidate after the inner agent has accumulated
   experience with it, with resource feedback; candidate evaluation needs repeated trajectories and memory
   rebuilding, so budget for it explicitly.
3. **Diagnose and edit from failures.** Mine hard cases or per-question failures, then propose design edits —
   crossover over prior designs and their outcomes, new routines added to a skill bank, or a new retrieval policy
   injected into a pool. Guard each edit with revert-on-regression.
4. **Keep design-selection data out of the report.** Questions that drive configuration evolution must not be the
   reported benchmark; skipping this — or reporting on a main evaluation of only 28 samples — is what leaves an
   unlabeled member's claim unverifiable.
5. **Certify transfer against a universal baseline.** Test the evolved design on held-out tasks and on different
   task regimes, and compare to a strong universal seed design; in one unlabeled member most transferred programs
   underperform such a seed. Ablate the evolved component and report variance across runs.

## Differentiation within parent
H19 and H20 edit the task agent or the improver's own code (single lineage or archive); H21 leaves both alone and
redesigns the separate experience-learning mechanism. Its fitness is therefore second-order — how well the agent
learns with the design — rather than how well one agent or improver performs. H21 members may still use an
archive or population, but that search machinery is a tool, not the claim.

## When to pick this one
Pick H21 when agents fail because a fixed, hand-built memory or context design encodes assumptions that transfer
poorly — stored experience becomes misleading as task regimes shift, or retrieval infrastructure no longer matches
heterogeneous memory. The tell is that the task policy is adequate but cross-episode reuse is the bottleneck. If
the proposer of changes itself plateaus, H19 fits; if many agent variants must be branched to escape local optima,
H20 fits.

## Tactical failure mode
The root assumption that fails is that **a learning mechanism evolved on one task regime is a general mechanism**.
Members state the limits: transfer is shown within related agentic task regimes, and fundamentally different
embodied tasks may need renewed evolution; most transferred programs underperform a universal seed; aggregate
optimization leaves some categories underserved. A second assumption is that redesigning retrieval can repair
missing knowledge — retrieval edits cannot recover absent memories. Further gaps: extra adaptive modules suffer
data starvation on moderate-length streams; evolution depends on the diagnostic model's capability; behavioral
contrasts used as a verifier do not verify task correctness.

## Lessons
### From accepted work
- Treat the whole architecture that encodes, stores, retrieves, and manages experience as the searched object, and
  score it with task performance plus resource feedback from inner-loop learning.
- Evolve executable skills by deliberative crossover over prior skills and their evaluated outcomes.
- Separate an evolving vocabulary of memory operations from the policy that composes them, and mine failures to
  grow the vocabulary.
- Archive candidate designs with their logs so later proposals can reflect on what was tried.
- Report held-out tasks and ablate the retained design; most accepted members here do both.
### From rejected work
- No member is labeled rejected (0 of 8), so no rejection lesson can be drawn; the cautions below come from stated
  limitations of accepted and unlabeled members, not from outcomes.
- Evolving a configuration on the same questions that are reported makes the gain uninterpretable.
- Compare transferred designs against a universal seed; a per-task design that loses to it is not a win.
- Do not use behavioral contrasts as a substitute for a correctness verifier.
