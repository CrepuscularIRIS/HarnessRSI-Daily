# H26 — Train the Curator on Downstream Utility
_parent: **Amortize the Improver into a Trained Policy** (`amortize_improver_into_trained_policy`) · corpus support: 17 papers (accepted 3 · rejected 1 · unlabeled 13)_

## Tactical pattern
The component that maintains persistent state — the memory writer, memory manager, skill extractor, or skill-library
curator — is turned from a prompted heuristic into a trainable policy. Its actions (store, update, merge, delete,
summarize, select) are credited by what happens *later*, when a consumer uses the written memory or skill on a
different query or a subsequent related task, usually by grouping tasks into streams or chains so that the reward of
task k+1 flows back to the curation action taken after task k. The decisive design choice is the credit path: reward
must come from downstream use of the artifact, not from the episode that produced it, and the writer is often trained
jointly with (or explicitly aware of) the reader that consumes it. Success is certified by beating a zero-shot or
heuristic curator on held-out tasks with the curated store frozen, and by an ablation that removes or freezes the
retained artifact to show the gain lives in what was written rather than in extra policy training.

## Step-by-Step
1. Name the curation operations as an explicit, finite action set (write, edit, merge, prune, retrieve-filter) so each
   can receive credit; a fixed tool set is acceptable, but say so as a scope limit.
2. Build the credit path: group related tasks into streams or chains so a curation action is rewarded by the success
   of *later* tasks that read the store. Rewarding the generating episode alone collapses this back into ordinary RL.
3. Couple writer and reader: either train them jointly with a shared policy, or make the writer's reward depend on what
   the reader actually retrieves and uses. A writer optimized in isolation against a composite proxy reward (validity,
   compression, format) on top of task accuracy is the configuration the one rejected member used.
4. Separate evolution from evaluation: build the store only from training streams, freeze it, and report on unseen
   tasks; never let skill extraction, bank construction, or verification touch test instances, and do not rely on
   privileged task-family labels or scenario metadata at retrieval time unless they exist at deployment.
5. Ablate the artifact, not just the optimizer: compare trained curator vs prompted curator with the same executor,
   and report store-removed and store-frozen variants plus training cost.

## Differentiation within parent
H26 trains the component that owns *persistent state* (memory, skill bank, experience graph); its outputs survive
across tasks and are consumed by someone else later. H27 trains the *proposer* of a one-shot artifact change or design
(an edit, reflection, prompt, workflow, or algorithm) whose value is measured immediately as a score delta on the
current query or next episode. H26's hard problem is delayed, cross-task credit; H27's is variance in a single-step
improvement signal.

## When to pick this one
Pick H26 when the improvement lives in a growing store that is read many times, the same curation decisions recur
across a task stream, and a delayed downstream success signal exists. The tell: a prompted curator writes plausible
entries that are rarely retrieved or help only the task that produced them. If the artifact is consumed once and
discarded (a per-query prompt, workflow, or reflection), H27 fits better.

## Tactical failure mode
The root assumption that fails is that the downstream reward cleanly measures the curator: in practice the store is
built or verified on the very tasks it is scored on, or retrieval leans on privileged grouping metadata, so measured
utility is partly leakage. Members' own limitations show this repeatedly: 5 of 17 concern evolution/evaluation
separation (extraction on test tasks, preparatory passes over test tasks, verification on the originating task,
online accumulation during evaluation, or separation not stated) and 3 of 17 depend on task-family or scenario
labels to form groups or retrieve. A second variant is noisy credit: set-level or self-judged rewards that cannot
isolate one entry's utility. A third is scope: 4 of 17 confine evaluation to a single domain or benchmark.

## Lessons
### From accepted work
- Training memory operations purely from downstream answer correctness, with no operation-level labels, is enough to
  replace heuristic add/update/delete rules when retrieval is also filtered before answering.
- Co-train the curator with the policy that consumes its output so the stored skills track the shifting rollout
  distribution instead of going stale.
- Make the writer reader-aware: reward construction by whether the reader can actually traverse to the needed evidence.
- Report an ablation that removes the curated store; 2 of 3 accepted evidence blocks do.
### From rejected work
- A composite reward (task accuracy plus validity, format, and compression terms) on an isolated writer invites the
  question of which term does the work; isolate it.
- Excluding the hardest sub-evaluation (conflicting or updated facts) from the reported suite reads as a gap, not scope.
- Large training budgets need a matched-budget prompted-curator baseline to justify the cost.
- With only 1 rejected member, treat these as warnings, not a measured rejection profile.
