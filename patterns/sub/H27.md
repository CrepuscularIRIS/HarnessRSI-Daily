# H27 — Train the Proposer to Amortize Search
_parent: **Amortize the Improver into a Trained Policy** (`amortize_improver_into_trained_policy`) · corpus support: 28 papers (accepted 10 · rejected 11 · unlabeled 7)_

## Tactical pattern
The model that proposes a change — a prompt editor, reflector, instruction inducer, workflow or multi-agent-system
generator, heuristic or algorithm generator — is trained by RL or preference optimization on the measured improvement
its proposals cause: the score difference before vs after an edit, the change in the next episode's return, or the
execution score of a generated design. One query-conditioned forward pass then replaces repeated per-task black-box
search. The decisive design choice is the reward's reference point (improvement relative to the pre-edit state or a
baseline, not raw score) and the proposer's conditioning (per query or per task, not one global artifact). Success is
certified by beating both the search procedure it amortizes and a prompted, untrained proposer of the same size, on
queries or task families the proposer never trained on, while accounting for the search and training cost saved.

## Step-by-Step
1. Identify the recurring search you are amortizing (prompt search, workflow search, reflection, heuristic design) and
   measure its per-query cost; the claim is "same or better result for less search", so the cost must be on the table.
2. Define a delta reward: score after the proposal minus score before it (or a dominance / score-gap preference),
   and condition the proposer on the query. A raw-score reward without a reference point makes edit quality and
   query difficulty indistinguishable.
3. Make the proposer produce a new kind of object, not just optimize the old one with a new loss: a query-conditioned
   distribution over designs, a single-pass system program, a self-rectifying generator team. Swapping the optimizer
   (SFT+RL, distill+RL, group-wise offline variants) on an existing generator formulation is where 3 of the 4
   high-fit rejected workflow/system generators sit.
4. Keep the proposer central: the trained component must be the improver of a harness artifact. 7 of 11 rejected
   members are low-fit (the learned policy is a controller, data acquirer, or generic optimizer at the edge of the
   pattern) versus 2 of 10 accepted.
5. Evaluate on held-out queries and unseen task families with a frozen executor, compare against the prompted
   proposer and the search baseline at matched budget, and never select the reported checkpoint on the reused holdout.

## Differentiation within parent
H27 trains the *proposer* of a one-shot artifact change or design whose value is scored immediately on the current
query or the next episode. H26 instead trains the *curator* of persistent memory or skill state whose value arrives
later, on other tasks that read it. H27's central risk is a noisy single-step improvement signal and overfitting the
proposer to the tuning set; H26's is delayed cross-task credit and store leakage.

## When to pick this one
Pick H27 when the same expensive search is rerun per query or per task, a cheap execution score exists, and the
best artifact plausibly varies with the query. The tell: a prompted optimizer gets good results only after many
evaluation calls per query, and those calls dominate cost. If the improvement should accumulate across tasks in a
store that is read later, H26 fits better.

## Tactical failure mode
The root assumption that fails is that training the proposer is itself the contribution. Rejected high-fit members
mostly keep the established "generate candidates, execute, score, train the generator" loop and change only the
training recipe or the reward terms, so reviewers see an optimizer variant of a known formulation. Rejected low-fit
members attach the pattern to a problem where the "proposer" is a generic control policy (prompt actions for output
regulation, data acquisition, code rewriting), so the amortization story is thin. Accepted members' own limitations
flag the residual risks: holdout reuse for checkpoint selection, separate policies per domain, dependence on fixed
operator spaces or template pools, and white-box or weight access to the proposer.

## Evidence profile
Counted over the 4 of 28 members that are corpus (arXiv full-text) papers with an `evidence` block, all accepted;
n = 4. Rejected members are mostly abstract-only OpenReview records, so evidence and limitations are not comparable across outcomes.
- Cross-task: yes 3, unclear 1. Held-out separation: yes 1, unclear 3.
- Improver comparison (trained vs prompted proposer): yes 2, unclear 2.
- Budget matched: yes 1, unclear 3. Optimizer cost: yes 1, unclear 3. Retained ablation: yes 1, unclear 3.
- Variance and leakage guard: unclear in 4/4. Code: announced 1, unclear 3.
Typical report: transfer across task families and a comparison against the untrained proposer. Typical omission:
seed variance, a leakage guard on the holdout used for selection, and the amortized search cost.

## Lessons
### From accepted work
- Reward the improvement relative to the pre-edit state or the previous attempt, not the absolute score.
- Condition the generated design on the query and price its cost (calls, tokens, early exit) inside the objective.
- Show the trained proposer beats a prompted proposer of the same model; 2 of 4 accepted evidence blocks do.
- Generate the whole system in one pass, or make the generator self-rectifying, so the trained object is new.
- Meta-train across many diverse task families so the proposer compresses examples into reusable instructions.
### From rejected work
- Changing only the optimizer (offline group-wise variants, SFT then RL, distillation then RL) on an existing
  workflow-generator recipe reads as incremental.
- Adding a single desirable property (robustness to paraphrase, safety feedback) to a known generator loop needs
  evidence that the property, not extra training, drives gains.
- If the learned policy is a generic controller rather than an improver of a harness artifact, the amortization
  framing will not carry the paper.
