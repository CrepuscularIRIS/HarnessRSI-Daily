# H28 — Couple In-Context Adaptation with Weight Training
_parent: **Couple Context-Level and Weight-Level Learning** (`couple_context_and_weight_updates`) · corpus support: 26 papers (accepted 7 · rejected 6 · unlabeled 13)_

## Tactical pattern
Treat the editable context layer (memory, skill library, system prompt, harness) and the model weights as two
levers of one learning loop rather than two separately tuned systems. Three variants recur: (a) *internalize* —
validated context (successful trajectories, distilled lessons) is pushed into parameters, adapters or learnable
prompt/latent tokens so it stops costing context; (b) *co-train on shared rollouts* — the same on-policy rollouts
score context candidates and drive the policy-gradient update, so each lever trains on data the other shaped;
(c) *arbitrate* — a controller watches progress and chooses a scaffold edit or a weight update when one stalls,
often on different timescales (fast context injection, slow idle-time training). The decisive design choice is the
coupling interface: what artifact crosses from context to weights (curated trajectories, skill-conditioned inputs,
reward signals) and under which version of the context it was collected. Success is certified by showing the
coupled system beats each lever alone on tasks the loop never trained or adapted on.

## Step-by-Step
1. Name the plateau. Show that context-only adaptation saturates or bloats (memory grows past context limits, raw
   trajectories stay noisy) *and* that weight-only training is sample-inefficient on the same tasks; without both
   halves the coupling has no motivation.
2. Give the context artifact an explicit, typed role. Separate declarative guidance (what to do) from procedural
   competence (how to do it), or skill text from the policy that conditions on it; an undifferentiated memory
   side-car bolted onto RL leaves reviewers unable to say which lever produced the gain.
3. Define the crossing. Decide which rollouts become training data, filtered by outcome and tagged with the context
   version that produced them; reuse matched rollouts for both levers where possible instead of composing two
   optimizers in sequence.
4. Ground the reward outside the model. Use verifiable outcomes or an independent checker for both curation and
   the weight update; self-reward that mistakes confidence for correctness, or adapting on the evaluation stream
   itself, is the boundary the rejected members with stated limitations crossed.
5. Certify with lever ablations under a clean split: context-only, weights-only and coupled, on held-out tasks,
   with seeds, variance and matched rollout budget. Report the cost of the slow loop (RL compute, teacher calls,
   experience-base maintenance).

## Differentiation within parent
H28 is the only sub-pattern of its parent in this bundle, so there is no sibling Hxx to contrast. Internally,
variant (a) ends with a smaller context and an altered model, (b) keeps both levers live and co-adapting, and
(c) keeps them separate but schedules them; choose the variant before designing the experiment, because each needs
a different ablation (does the internalized model still need the memory? does sharing rollouts beat sequencing?
does the arbiter beat a fixed schedule?).

## When to pick this one
The tell: a context-level loop already works but has hit a ceiling (memory too long, skills not followed reliably
by the executor, gains flat across rounds), and you have a verifiable reward and the compute for policy updates.
If no weights can be touched, or no verifier exists to curate trajectories, stay at the context level instead —
this card adds an L1 dependency for a harness-level problem.

## Tactical failure mode
The root assumption that fails is *"experience that helped in context is clean training signal."* Members break it
three ways: rewards come from self-confidence or from scores on the very tasks later reported; training and
evaluation pools overlap (limitations of 6 of 26 members flag train/eval overlap or test-derived feedback); and the
coupled loop is claimed but not exercised end-to-end (two unlabeled members show only one round with no model
update, or separate harness and model case studies instead of a coupled cycle). A second, rejected-side signature is mechanism weight:
capacity expansion, bi-level meta-RL or module-grouped policy gradients carry the contribution while the context
lever is secondary, so the "coupling" claim rests on composition rather than on a shared interface.

## Lessons
### From accepted work
- Let one stream of on-policy rollouts both rank context candidates and update the weights; shared data is the cleanest coupling interface.
- Split the roles: refine declarative knowledge in context while RL improves procedural execution, so each lever has a job the ablation can isolate.
- Make the skill or memory library an input the policy is trained to condition on, and revise it from diagnosed failures, not only successes.
- Compress trajectory-heavy experience into small learnable tokens or adapters on a frozen backbone, keeping recent insights as text alongside.
- Turn retrieved test-time memories into curated training data, so the memory pays for itself after it is internalized.
### From rejected work
- Self-generated confidence used as reward drifts toward confident-but-wrong traces; anchor curation in verifiable outcomes.
- Adapting on the same stream you report on invites a leakage objection that no ablation fixes.
- Stacking heavy weight-side machinery (capacity growth, bi-level meta-RL) with a memory side-car blurs which lever earned the gain.
- Composing an existing RL method with prompt optimization in sequence reads as integration unless a shared interface is shown.
- Narrow task coverage and weak small-model self-distillation cap claims of general self-evolution.
