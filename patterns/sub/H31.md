# H31 — Use a Statistically Sound Commit Rule
_parent: **Gate Retention on Measured Evidence** (`evidence_gated_retention`) · corpus support: 15 papers (accepted 2 · rejected 0 · unlabeled 13)_

## Tactical pattern
Proposing a change to the agent, harness, prompt state or policy is separated from authorizing it. A candidate
replaces the incumbent only after it clears a rule whose error properties are known: strict improvement on a
validation split disjoint from the one used to propose it, example-level pass-to-fail and fail-to-pass gating, a
paired test or anytime-valid e-process that accumulates evidence per candidate, a drift index with stopping
rules, or a sealed external audit the agent cannot see or edit. Theoretical members state when self-modification
preserves goals or bounds value loss. The decisive design choice is where the verdict comes from: a source the
proposer does not control and data it did not reuse. Success is certified by a fallback that never regresses
(an empty or prior state survives when edits fail) and by a guarantee or audit that holds per committed change.

## Step-by-Step
1. Fix the incumbent and a rollback point (including an empty-state fallback) before any proposal is generated.
2. Split proposal data from commit data; reusing development cases for both proposal and gating is the most
   common leak among members, and online updates on test batches invalidate the comparison.
3. Choose the commit statistic for the noise you have: paired evaluations with sequential evidence when scores
   are noisy, example-level regression checks when aggregates hide regressions, a drift index when quality can
   rise while constraints erode.
4. Keep the auditor out of the agent's reach: self-written tests cannot authorize deployment when the same agent
   edits policy and verifier; return only accept or reject from a hidden task-native audit.
5. Report per-candidate versus run-level guarantees, power (small true gains can be rejected), seeds, and the
   optimization budget against baselines. For theory, state the rationality and knowledge assumptions under which
   the guarantee holds and whether errors compound.

## Differentiation within parent
H31 is the acceptance rule for whole-system updates, including formal analyses of when self-modification is safe.
H29 values individual memory entries and H30 governs library membership; both manage many items, while H31 makes
one commit-or-reject decision about a single incumbent.

## When to pick this one
The tell: one evolving artifact, a noisy or reused development set, and a history of edits that raised the dev
score but regressed solved cases or drifted from constraints. Pick H30 when many entries enter and leave a shared
pool; pick H29 when the incumbent is fixed and only memory ranking changes.

## Tactical failure mode
The root assumption that fails is that a positive score difference on the data the proposer saw is evidence of
improvement. No labeled member was rejected, so the failure mode is drawn from limitations across members:
development cases reused for proposal and gating, critic determinism assumed, baselines without matched budgets,
single runs or one split seed, validation non-regression that does not guarantee test safety, guarantees that
hold per candidate but not per run, composed loop guarantees left as conjectures, and theory that assumes optimal
or bounded-error agents. One accepted member itself lists conceptual rather than measured baselines and internally
inconsistent counts, a reminder that acceptance is not a quality certificate.

## Lessons
### From accepted work
- Separate error types in self-modification analysis: optimization errors can compound across modifications
  while knowledge errors need not, so the safety argument depends on which one dominates.
- Treat apparent quality gains under iterative refinement as suspect until drift from constraints and regression
  of earlier gains are measured and can halt the loop.
- Prioritize constraints over capability in the stopping rule.
- State worst-case assumptions (bounded errors, unlimited modification, no corrigibility mechanism) openly.
### From rejected work
- No labeled rejected member exists in this sub-pattern; the cautions below come from unlabeled members'
  stated limitations and are not outcome evidence.
- A gate that reuses the proposal data is not a gate; hold commit data out.
- A non-regression gate does not require genuine improvement; report both.
- A run-level claim built from per-candidate guarantees needs its own argument.
