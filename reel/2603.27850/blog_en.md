# EffiSkill: mined "optimization skills" lift code-efficiency success; what the controls do and do not show

*A Reel interpretation of [arXiv 2603.27850v1](https://arxiv.org/abs/2603.27850v1) (HarnessRSI Daily score 67, ★★). Authors: Zimu Wang, Yuling Shi, Mengfan Li, Zijun Liu, Jie M. Zhang, Chengcheng Wan, Xiaodong Gu. The paper links no code repository; it states that data and artifacts are at https://doi.org/10.5281/zenodo.19249527.*

## What the system changes about itself

EffiSkill does not change model weights, and it does not edit itself at test time. It builds a **skill library once, offline**, and then reuses it. The library holds 29 **Operator Skills** (concrete slow-to-fast transformations such as "full DP to rolling state") plus a small set of **Meta Skills** (procedures for diagnosing, retrieving and composing operators). The paper does not give the number of Meta Skills.

**Stage I (mining).** From paired slow/fast solutions, gpt-5.1 writes a structured trace per pair (ProblemBrief, SlowAudit, FastAudit, DeltaSummary). Traces become compact signatures, are clustered in a hybrid TF-IDF plus all-MiniLM-L6-v2 space, and each cluster is distilled into a skill card; similar cards are merged (TF-IDF cosine threshold 0.8, then an LLM merge). The mining corpus is 900 Python and 900 C++ pairs, keeping only pairs with a speed-up ratio of at least 2. The paper states it checked that none of the mined problems overlap with the EffiBench-X tasks; it does not describe how.

**Stage II (inference, "execution-free").** For an unseen program the system diagnoses likely bottlenecks, retrieves 3 candidate sets of Operator Skills, has Meta Skills compose 2 to 3 plans per set, and generates candidates from the plans. Candidates are never run inside this loop. There is no keep/reject rule for the library itself: it is fixed after Stage I. (A separate selection step, applied to every method, keeps candidates that pass the public tests, 20% of each task's tests, and ranks them by public-test runtime.)

## Headline result, as reported

EffiBench-X, 623 tasks, canonical expert solution as the input program, k = 8 candidates per method per task, same backbone for all methods, one value per cell (the paper describes no repeated generation runs or seeds; it averages 3 executions per candidate to reduce runtime noise). OPT@k is the share of tasks where at least one of the top-k candidates passes all private tests and is at least 10% faster than the input. Table 1, OPT@8 (%), EffiSkill against the **highest baseline in that column**:

| Setting | EffiSkill | Strongest baseline |
|---|---|---|
| GPT-5-mini, Python | 37.40 | 32.42 (FasterPy) |
| GPT-5-mini, C++ | 66.77 | 54.74 (CoT) |
| Qwen3-Coder-30B, Python | 36.60 | 28.25 (FasterPy) |
| Qwen3-Coder-30B, C++ | 56.50 | 43.98 (SBLLM) |

EffiSkill has the best OPT@1 and OPT@8 in all four settings. The OPT@1 gaps to the strongest baseline are smaller: 5.29‡ (GPT Python), 3.69 (GPT C++), 5.30‡ (Qwen Python), 5.78‡ (Qwen C++). The abstract's "3.69 to 12.52 points" is the minimum and maximum over these eight gaps and matches the table.

## The controls that decide whether the gain is real

- **Significance.** One-sided paired bootstrap over the 623 tasks against the best non-EffiSkill baseline in each setting: p < 0.05 in seven of eight cells; GPT-5-mini C++ OPT@1 (44.62 vs 40.93) is only p < 0.10. The bootstrap resamples tasks; the paper describes no repeated generation runs or seeds and reports no run-to-run variance for any method, and it mentions no correction for the eight tests. One task is 0.16‡ points.
- **Ablation (Table 2; it has no language label, but its full-system rows equal the Table 1 Python cells, so we read it as Python; one value per cell, no SD).** GPT-5-mini OPT@1 / OPT@8: full 26.48 / 37.40; without retrieval 12.20 / 27.45; random skills from the library 13.80 / 27.82; single plan per bundle 18.78 / 25.84. Qwen3-Coder: full 21.35 / 36.60; without retrieval 7.22 / 9.15; random skills 12.36 / 13.80; single plan 11.88 / 14.29. Retrieval of *relevant* skills and multiple plans both matter, and the paper concludes "Together, these components account for the gains". The rows also show that all six ablated rows have OPT@8 below the plain **Instruction** baseline (31.62 on GPT-5-mini, 24.40 on Qwen). Only "without retrieval" removes skills altogether (it generates directly from the diagnosis brief); the other two rows still use skills, and the Qwen rows (9.15 to 14.29 against 24.40) look like degraded pipelines rather than a clean attribution to the library. The paper does not say how 8 candidates arise from 3 skill sets with 2 to 3 plans each, so it cannot be checked that the single-plan row yields a comparable candidate set. The paper lists "diagnosis" among the components but has no without-diagnosis row, no Meta-Skill ablation, and no control with non-mined (for example hand-written) skills, so the value of mining from slow/fast pairs, as opposed to supplying any optimization tips, is not isolated. The random-skill row draws from the same mined library.
- **Budget.** All methods get the same k = 8 candidates. The paper reports no tokens, LLM calls or wall-clock per task for any method, and no Stage I cost (gpt-5.1 traces for 1,800 pairs, clustering, merging). The pipeline has several stages (diagnose, compose plans, generate) and the paper does not state how many LLM calls they take, so the budget is matched on candidates only, as far as can be checked.
- **What the baselines were given.** The paper describes none of them as receiving the mined skill library or the gpt-5.1 traces. RAG retrieves pairs "from PIE" and FasterPy retrieves summaries from "historical code transformations"; the paper does not say whether they used the same 900 + 900 pairs, which for Python also draw on Mercury, Code Contests and APPS. SBLLM is, in the paper's words, a single-iteration variant without execution-based selection adopted "for fair comparison"; we read it as a weakened adaptation (our reading), and its numbers swing from 8.67 (Qwen, Python, OPT@8) to 43.98 (Qwen, C++). The fine-tuned baseline EffiCoder appears only for Qwen and is never the strongest; the paper does not say whether the authors fine-tuned it or used a released checkpoint, or on what data. Baseline tuning budgets and sampling settings are not reported.
- **Held-out.** The mined problems and the evaluation tasks are different problems, with a stated overlap check; both come from competitive programming and the authors note that "some distributional similarity may remain". Contamination of the backbones or of gpt-5.1 is not discussed. The paper does not say how the design constants (merge threshold 0.8, 3 skill sets, 2 to 3 plans, k = 8) were chosen.
- **"Cross-language transfer".** RQ3 asks whether EffiSkill remains effective "when transferred from Python to C++", and its answer says EffiSkill "generalizes across Python and C++ at the framework level". The mining corpus contains 900 C++ pairs as well as 900 Python pairs, so this is not a zero-shot transfer of Python-mined skills. The paper reports one 29-skill library and does not say whether the library is pooled across languages or built per language.

## Where the gain is absent or small

- **OPT@1 gains are modest** (3.69 to 5.78‡ points above) and one cell is only p < 0.10. The large gaps (12.03 and 12.52) are OPT@8 on C++; on Python the OPT@8 gaps are 4.98 and 8.35.
- **Headroom remains large.** EffiSkill's Python OPT@8 is 37.40 and 36.60, so 62.60‡ and 63.40‡ percent of Python tasks still have no qualifying candidate at k = 8.
- **Text vs table.** The introduction gives the Qwen gaps as 12.36 (C++) and 8.67 (Python), and the RQ3 answer box says "up to +12.36". Table 1 and Section 5.3 give 12.52 and 8.35 (OPT@8 against SBLLM and FasterPy); no Qwen3-Coder baseline row gives a gap of 12.36 or 8.67 on either metric. We use the table values.
- **Task-level comparison (Figure 5).** The paper says EffiSkill wins on more tasks than it loses "against the strongest non-EffiSkill baselines": 455 / 26 / 142 (wins / ties / losses of 623‡, read off the figure) vs SBLLM, 401 / 41 / 181 vs EffiCoder, 348 / 34 / 241 vs CoT, 313 / 103 / 207 vs Instruction. Only the CoT panel compares with the Table 1 leader. In the other three panels the comparator (SBLLM, EffiCoder, Instruction) is not the highest-OPT@k baseline in Table 1 (FasterPy, FasterPy or CoT, SBLLM). The paper does not define "strongest" for this figure, so the "broadly distributed" claim is not checked against the Table 1 leaders.
- **Skill usage is concentrated in one family.** Table 3: the implementation and constant-factor family is 54.2% of candidate-skill pairs; algebraic/closed-form 19.7%; DP/state compression 13.1%; combinatorics and number theory 9.5%; graph/data-structure 3.5%. The paper says the smaller number-theory family is "associated with larger average gains" but gives no numbers; it also says the algebraic and DP families appearing frequently shows the library is "not limited to local cleanups".
- **One illustrative case.** The chmax-rush! example runs 3838.11 ms for the prompting candidate and 1434.23 ms for EffiSkill (2.68×); the paper calls it "a representative success case" and says it is "not intended to demonstrate the largest absolute gain".

## Our read

HarnessRSI score **67**, band ★★, evidence level **retained**: the retained artifact, a mined skill library, is evaluated on tasks not used to build it, and the pipeline is not shown to improve its own improver. The paper **reports** a held-out evaluation with a stated mining-vs-benchmark overlap check, ablations (Table 2, read as Python) that remove or randomize the retrieved skills, a paired bootstrap over tasks, and the same candidate count for all methods. It **does not report** run-to-run variance (generation seeds), tokens/LLM calls or mining cost, a without-diagnosis or non-mined-skills control, or a check for contamination of the backbone models. Judgment note: our record marks `retained_ablation` as unclear, but Table 2 does remove or randomize the retrieved skills (read as Python, one value per cell). The result should be read as: a consistent edge on one benchmark and two backbones, strongest on C++ OPT@8, with unreported inference cost.
