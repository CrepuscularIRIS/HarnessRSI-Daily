系统类 · F1 / F5 · 归因与修补现任 harness

别给提议者看摘要：让它自己翻原始执行轨迹

Meta-Harness 把所有历史候选的源码、分数和完整执行轨迹放进文件系统，由编码代理按需 grep / cat 后提出新的 harness 代码。同样的评估次数下，能读原始轨迹的接口明显好于只给分数或摘要的接口。

问题

harness 的错要过很多步才显现，压缩后的反馈找不到源头

一个“存什么、何时取、怎么给模型看”的决定，可能在许多推理步之后才让任务失败。只给标量分数、只给上一个候选或给一段 LLM 摘要，会把定位失败所需的细节压缩掉。作者把这看作现有文本优化器为可扩展性做的取舍，而不是长程依赖没有用的证据（§1）。

案例

为什么要原始轨迹：一次搜索日志里的归因

TerminalBench-2 · 附录 A.2 · 基线 KIRA 64.4%（该搜索设置）
第 1–2 轮58.9 / 57.8
两个不同的结构修复都附带同一份清理型 prompt 改写，均退步
第 3 轮：识别混杂63.3
推断共同因素是 prompt 改写，单独保留结构修复，退步明显变小
第 4–6 轮仍退步
继续改完成流程与等待逻辑，得出“改 prompt / 控制流风险高”
第 7 轮：纯增量本轮最佳
首轮前注入环境快照（语言、包管理器、/app 列表），不改其他方法

限制

  1. 接口消融只在文本分类的 search set 上，每个条件一次搜索，没有方差。
  2. 只用一个提议者（Claude Code + Opus-4.6）；作者自己指出换提议者的效果尚未研究。
  3. TerminalBench 搜索与报告同一套题，不能当泛化证据。
  4. 数学“5 个留出模型”中 GPT-OSS-20B 就是选择 harness 用的模型；数学 search set 在 §4.2 写 250 题，附录 D 写 88 题。
  5. 对照只匹配评估次数，不匹配提议者 token 和墙钟成本。
  6. 迭代日志是定性案例，不是“轨迹访问导致收益”的受控证明。
