# Socratic-SWE：把修复轨迹变成下一轮课程——但回路里也在训练模型权重

*Reel 解读：[arXiv 2606.07412v1](https://arxiv.org/abs/2606.07412v1)，完整标题 **Socratic-SWE: Self-Evolving Coding Agents via Trace-Derived Agent Skills**（HarnessRSI Daily 评分 64，★★）。未提供代码链接。实际读的是 v1；任务指出原候选元数据误列不可用的 v2，详见 SOURCE.md。*

## 系统改变了自己的什么

Socratic-SWE 把仓库修复的成功、失败轨迹提炼为 **Agent Skill Registry（智能体技能库）**，再据此生成下一轮训练任务。每项技能是结构化文档，包含名称、自然语言描述、适用条件、有序操作。轨迹包括仓库检查、编辑、命令执行和测试结果；Qwen3.6-27B 从中提取成功策略和纠错原则，经过语义去重、轨迹覆盖度过滤后入库（§3.2）。

技能用于引导 **Generator**，不是直接给一个冻结权重的 Solver 注入技能库后做推理评测。Generator 与 Solver 共享 Qwen3.5-9B 权重，分别采用 GRPO 与 GDPO 更新。因此留存的变化既有任务课程、技能，也有**训练后的模型权重**。我们的理解是：结果支持轨迹驱动的训练课程，而非冻结权重、纯 harness 改进。

## 迭代回路与保留/拒绝规则

1. 当前 Solver 产生成功、失败轨迹，提取器把重复出现的行为归纳为技能。
2. Generator 根据技能、仓库上下文和 Solver 反馈提出修复任务。实现提示词要求在一个生产文件里注入可逆的语义错误，原代码作为参考修复，不能修改测试（附录 G）。
3. 候选必须通过**格式、仓库定位、执行稳定性、语义与可解性**检查。OAuthLib 示例还要求：目标测试在注入后失败，逆转补丁后通过，重复运行稳定，问题描述不泄漏 oracle 补丁（附录 H）。
4. Generator 获得 `Valid × cosine(候选任务的 Solver 梯度, 验证集梯度)` 奖励。参考方向来自可信的 BeyondSWE 任务，每轮刷新。这是**训练奖励**，不是明确规定“只有正对齐任务才能入池”的硬门槛：公式 2 与算法 1 按 `Valid = 1` 接收任务。附录 D/F 谈及按奖励选择，却未给额外截断阈值；具体选择实现仍未交代清楚。
5. Solver 在接收的任务上训练，奖励包含完全通过、部分修复、避免回归。Solver 可见任务描述与仓库反馈，看不到 Generator 的参考解或验证器内部信息（§3.4）。更新后的行为产生下一轮轨迹。

**初始化与刷新步骤交代不足。** §3.2 在种子任务集上收集轨迹，附录 B 却称 Socratic-SWE 只从种子仓库开始，没有预先存在的 SWE 任务或修复轨迹。算法 1 把课程与技能库作为输入，也未显式列出技能库刷新。论文没有协调这些启动与更新细节，我们不猜实际运行了哪种实现。

## 论文报告的主要结果

表 1 使用 **Qwen3.5-9B**，迭代三轮，每轮 **12k 个验证通过的训练实例**，共 **36k**。SWE 修复用只暴露 Bash 的 mini-swe-agent，Terminal-Bench 用 little-coder。评测分别为 SWE-bench Verified（500 个 issue）、Lite（300）、Pro Public（731）和 Terminal-Bench 2.0。

| 最后一轮通过率（%） | 基础智能体 | SSR | Socratic-SWE |
|---|---:|---:|---:|
| SWE-bench Verified | 42.60 | 47.00 | **50.40** |
| SWE-bench Lite | 29.67 | 34.00 | **36.67** |
| SWE-bench Pro Public | 17.24 | 20.66 | **22.85** |
| Terminal-Bench 2.0 | 10.11 | 12.36 | **14.61** |
| Overall：基准间均值 | 24.91 | 28.51 | **31.13** |

SSR 是每列最后一轮最强基线，其中 Terminal-Bench 与 Socratic-Zero 并列。论文报告 Verified 比基础智能体高 +7.80 个百分点，比 SSR 高 +3.40。收益并非仅来自一个基准：相对基础模型分别提升 +7.80、+7.00、+5.61、+4.50，绝对增幅以 Verified/Lite 较大。但没有分仓库结果，无法判断基准内部是否由少数仓库贡献，且只评测了一个 Solver 模型。

**Overall 是跨基准平均，不是跨随机种子均值。** 表 1 及各消融没有交代种子身份、训练/评测重复次数、标准差或置信区间。不能据此推断只有一次运行，也不能判定统计显著性。

## 决定收益是否可信的对照实验

- **技能库与轨迹消融（表 2，Verified，第三轮）。** 完整系统 50.40；去技能库 46.20；手工技能替代轨迹提炼 48.00；用 GRPO 替代 GDPO 48.60。支持技能、轨迹内容和 Solver 优化各有贡献，但没有把纯推理期技能库的作用与权重学习分离。
- **奖励对照（表 3、6）。** Hardness 47.40，uncertainty 48.20，高斯 variance 48.80，梯度对齐 50.40；未归一化内积 49.40。梯度与难度混合达到 **50.60**，因此默认配置不是全文所有变体中的最好成绩。
- **提取器对照（表 2）。** Qwen3.5-9B 自提取 49.80；默认 Qwen3.6-27B 50.40；Claude Opus 4.5 提取 51.00。这是提取器变体，不是多种子重复；0.60 个百分点的差异没有不确定性估计。
- **预算与各基线可用的信息（附录 B）。** 论文称各自进化方法的 Solver 架构、harness、交互预算和验证通过的实例数相同。需要种子任务的基线得到 10% 的 SWE-smith 任务，但未逐一说明每种方法对应哪种初始化。SPIRAL 使用缺陷注入/修复的零和自博弈、角色条件优势估计。R-Zero 使用 Challenger 生成任务、Solver 多数投票奖励。**Absolute-Zero 确实有执行验证**，但没有结构化错误产物或技能引导。Socratic-Zero 使用 Qwen3.5-397B Teacher，并让 Generator 蒸馏其任务设计策略。SSR 用代码删除/历史回退制造错误，做执行一致性检查，Solver 获得二元通过/失败奖励。没有报告基线获授与 Socratic-SWE 相同的轨迹技能库或 BeyondSWE 对齐奖励。也未报告各基线的调参预算；不能笼统说它们都没有验证或蒸馏。
- **验证集与默认配置选择（附录 E）。** 100 个 BeyondSWE 任务不进入 Solver 训练或最终评测，但其梯度引导生成，因此它是课程优化信号，不是完全未触碰的最终测试集。验证集大小敏感性实验的指标是 **SWE-bench Verified**：20 个任务为 49.20，100 个为 50.40，200 个为 50.60。作者据此论证默认取 100，但没有说明是否另有独立划分用于选择默认值/超参数。表 4 的两组独立 rollout 衡量的是梯度稳定性，不是基准评测运行间方差。
- **成本（附录 F、表 5）。** 8×A100-80G 上每轮 15.0 小时：任务提出/验证 4.2，Solver rollout/执行 7.8，策略更新 1.7，验证梯度计算 0.5，候选打分 0.8。论文称每轮对齐开销 1.3 小时，三轮 45 小时中约 3.9 小时，并称总 FLOPs 与 SSR 相当。但没有逐基线计时/FLOP 账本，没有单列技能蒸馏成本，也未明确提取器/Teacher 成本是否计入。表中大部分时间是 rollout/执行，但未把环境耗时与模型耗时分开。

## 增益缺失或较小之处

- **不是每个阶段都领先。** 第一轮 Socratic-SWE 的 Terminal-Bench 12.36，与 SSR 第二/三轮和 Socratic-Zero 第二/三轮相同。§4.2 只点名 SSR 与 Socratic-SWE 的终端收益“有意义”，但表 1 同样给 Socratic-Zero 12.36（+2.25）。我们保留这个并列事实，不暗示存在显著性区别。
- **小幅设计增益存在不确定性。** 混合奖励比纯梯度对齐高 +0.20，200 个验证任务比默认 100 个高 +0.20，都没有方差/置信区间；只能说数字更高，不能说已证实稳定提升。
- **固定池会饱和。** §5.1 扩展到五轮，报告 Verified 为 52.00，SSR 为 48.00，均接近平台期。这已超出三轮/36k 的头条预算。作者明确指出，这是固定仓库分布下的结果，不是开放式无穷改进。
- **泄漏与泛化范围。** 论文分别命名 BeyondSWE 验证数据与最终评测基准，却未列出种子仓库集合，也未证明训练轨迹与评测仓库/任务不重叠。因此轨迹来源与评测仓库的确切关系未知。通读全文未见基准重叠/去污染审计、预训练污染分析或时间划分。隐藏基准测试、不让生成的问题描述泄漏 oracle 补丁属于局部防护，不能证明不存在 SWE-bench 式污染。更广的仓库/语言迁移，以及没有可靠执行测试的场景，仍待验证。
