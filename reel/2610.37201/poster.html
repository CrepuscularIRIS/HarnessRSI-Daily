技能优化器报出的增益是选出来的还是学出来的？多出来的费用又记在哪一行？

GEPA、SkillOpt、SkillAdam 改写放进上下文的“技能”文本，在 ≤ 30 个开发任务（TB2 只有 9 个）上分数更高就保留。长时程任务成功率噪声大、上下文每回合重发——BiPA 不改优化器，只用日志回答两件事：开发增益里有多少是挑选本身造成的；多读的 token 来自哪种行为。

小票 04 · 计费方式§4.2–4.4 · Prop. 1 · Finding 8

多一回合，多付的不止一回合 示意

每回合都把前缀和全部历史重发一遍：回合多 1%，输入 token 至少多 1%，长回合接近 2%。实测同一任务内回合每多 10%，输入 token 多约 14–16%（斜率 1.35–1.58），而输出 token 与工具调用斜率 ≤ 1.03。

不降开发成功率又不增 token 的编辑5 / 59
AutoBench：写操作与别的写操作同回合（种子 → 学到的技能）56% → ≤ 0.3%

串行写有其道理：AutoBench 每次写都整体读改存模拟世界，并发写会互相覆盖——把所有调用按种子的密度打包，AutoBench 的 log ρ 从 0.17 减半到 0.08，大头正是这些写。也就是说，并非每个多出的回合都是浪费。

换模型、换基准：增益不跟走，费用跟走

迁移的 9 个技能只有 1 个高于种子（+1.9）；DeepSeek 学的 τ³ 技能在 Luna 上仍读 1.08–1.38×，TB2 技能在 AutoBench 上读 1.24–1.49×。

作者建议 · 四条设计原则§6
  1. 增益超过“仅靠挑选会报出的增益”才收；分不出成功率时，按超出运行间差异的 token 差来定。
  2. 按编辑新增的回合计费，而不是按文本长度。
  3. 允许编辑器删除与合并规则（DeepSeek 59 次编辑只缩短过 1 次）。
  4. 让编辑器看到之前规则花了多少回合与 token。

账单换算也不翻转结论：按缓存价计费仍为种子的 1.05–1.27×；按“只付本回合新增历史”重算（压缩历史的近似），回合斜率降到约 1.04，但每个技能仍是 1.05–1.36×。

边界 · 本项目阅读Limitations · 附录 A、C
  • 每个“优化器×模型×基准”只跑了一次优化；三次测试只反映执行噪声，不反映优化随机性。
  • 一个 harness（OpenCode，不压缩历史）、两个模型、同一个种子技能；规则 → 行为是对应关系，没有做单条规则的受控改写。
  • Luna 的 AutoBench 增益是真的；作者的“分不出成功率就看成本”规则在那里会退回种子，也会错过它。

本项目读法：“开发增益落在挑选噪声里”与第三期的 2610.28798、2610.30499 是同一判断，本篇的独立价值在后半——成本藏在回合里而不是技能长度里，且成功率指标看不见它。读法来自卡片 diagnose_self_improvement / evidence_gated_retention，非作者原话。
