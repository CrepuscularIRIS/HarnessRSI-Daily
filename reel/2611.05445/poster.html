用户只说“找到 Alice，我来转账”，
谁来想起要先登录？

检索器按与请求的相似度给每个工具单独排名，常常找到“目标工具”却漏掉它的前置工具。LIBRA 在任何请求到来之前，在沙箱里真跑一遍组合，只把“有它能成、换掉就败”的关系存进工具库，检索时沿边补回前置工具。

A · 问题

目标排第 1，前置排到第 169

请求通常只说想要的结果，认证、查 ID、初始化状态、格式转换这些步骤不写。前置工具与请求、与目标工具在嵌入空间里都不必相似——稠密检索按设计找到了目标，缺的是“谁必须先执行”的信号。

图 1 的例子：请求“Find Alice in my contact and I will make the transfer”，稠密检索给出 Venmo.Search_users；LIBRA 在库里查到它的输入来源边，沿一跳补回 Venmo.Login。LIBRA 不生成、不执行任务计划，只改变候选集。
B · 构库

反事实沙箱测试：有它能成，换掉就败

LLM 只看单个工具的公开描述、签名和输入输出模式，写出契约：候选调用、可复用的输出与状态变化、可观测的成功 / 失败条件。然后在隔离沙箱里组合执行：

C · 检索

只走一跳，每个输入至多补两个提供者

稠密检索取前 15 个工具作“消费者种子”，沿入边找提供者；每个输入只留字段名最匹配和与请求最相关的两个，再把种子分数传过去：

s′(u) = max( s(u), [ s(u) + Σt∈C(u) s(t) ] / (1 + |C(u)|) )

取平均而非求和，邻居多的工具不会因此占便宜。剪枝很要紧：把所有保留边的提供者都加进来，SciToolEval Recall 从 91.1 掉到 76.4；走两跳也略降（附录 E）。

关键对照：同一编码器，只换图

附录 B 表 4。未经执行过滤的“模式兼容图”与不用图几乎一样（AppWorld 29.2 vs 28.7）；换成执行过滤图才 +12.0 / +7.0 / +4.6 Recall。NDCG：39.1 / 86.6 / 78.4（QTS 32.8 / 83.9 / 76.2）。

每个构库作业 96 个 CPU worker、一张 L40S（字段嵌入），AppWorld 申请 384 GB 内存（附录 C）。LLM 调用随工具数线性增长，但候选组合最坏是工具数的平方级；工具数相近的 AppWorld 与 SciToolEval 耗时差 12.6 倍。

F · 读之前先知道
  • 只测了检索：Recall / NDCG 衡量候选集，不是工作流完成率；没有端到端任务成功。
  • 没有边级金标准：“运行时验证”只表示在测试的契约与沙箱状态下通过，作者不声称依赖精度；兼容边也算进图里。
  • 需要可执行、可重置的运行时；SciToolEval 只评了 530 题中可执行的 270 题，AppWorld 用公开注释的 90 训练 + 57 开发题。
  • TGR 原实现不公开，表中是作者的改编版；Ego-Trip 也按各基准改编。
  • 契约由 LLM 依公开元数据提出、最多按反馈修订两次（AppWorld 218、SciToolEval 48、BFCL 37 份契约至少修订一次）；契约没想到的组合，测试也测不到——反事实检验管精度，不管覆盖。
  • 依赖任务专属数据的前置（建库时没有那条联系人）结构上无法提前发现，这正是 AppWorld 漏检的大头。

改变的判断：从元数据推断“谁依赖谁”不够——模式兼容的边不加执行过滤，对检索几乎没有帮助；让组合关系先过“有它成、换掉败”的执行检验，才是这类冷启动工具库能复用的部分。
