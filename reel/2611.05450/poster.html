ReScopeBench 不只看任务分，还把代理存下的经验逐条对照“当前版本”的私有参考计分：过时内容的修订、仍有效内容的保留、记对之后的使用分开测。

1同一个任务分，三种记忆

交付目录搬了家，交付规则没变。下面三种结局可以拿到相同的任务分（§1）：

① 找到新目录，交付成功但记忆里旧路径没删，下次可能照旧走
② 改写了这条记录却把仍有效的交付规则一起丢了
③ 改对路径、保留规则才是想要的“选择性修订”

探索和执行共用环境预算：反复重新查找会挤占完成请求的资源，所以“每次都重查”不是免费的替代。

2研究动作：先定经验，再造任务流

环境准备代码实现的模拟应用，可复现初态，部分操作计费
经验发现读环境代码找出可经工具发现的结构 / 规则，建私有依赖图
联合合成共用经验的有序任务流 + 局部静默变化表（1–3 处）
回放冻结参考解按序回放、核预算与判分，冻结后才评模型

成对任务流：同一初态、同任务、同工具、同预算、同变化表。有经验流保留 memory / skills / 可检索历史；无经验流每题清空。两边都允许题内学习、每题新对话；环境状态随各自动作分叉。

SC / RC 结构 / 规则经验覆盖：评审模型读全部存档，逐条对照当前版本参考的评分细则
UC 首个受影响题之后，需更新内容已记对的比例
RT 更新内容与原先记对的仍有效内容同时到齐有多早（只记首次）
BP / EP / DP 无经验 / 有经验 / 变化首题的任务表现（确定性判分器）

经验评审用 GPT-6 Astra；换 GPT-6.1 Sol 重评 433,850 个判定，一致率 98.79%（结构）/ 99.24%（规则）——作者明说这只说明同一细则下稳定，不是准确性的独立验证。

保留经验确实有用：20 个模型平均 BP 18.38 → EP 59.82（本项目按表 2 计算）；但下面三块说明，任务分之外还藏着三种缺口。

3改动落后于保留

只取变化前已经记对的案例（排除“本来就没学会”）：487 个模型 × 经验单元 × 变化事件，覆盖 20 个模型、8 个环境、11 次变化。

到第 4 个受影响题，20 个模型中 19 个、8 个环境全部是“保留 > 改动”。曲线也受“什么时候才有题暴露新证据”影响；只计一对一替换，Railway / Cloud 的多对多替换被排除（附录 C.2.1）。

4立即更新：没有模型超过 37.63

表 2。商用模型 UC 中位数 29.75；紧凑开源 Qwen3.8-27B 为 29.05，另两个 Qwen3.5 低于 3。UC 与 RT 的排名不同：后续几题能补齐，不代表变化一来就改。UC / RT 都可能含“首次获得”而非修订。

5记对了，不等于交付了

Filesystem 与 Oracle 两个可逐条映射的环境：同一题内对比“所需经验在上一检查点已全部记对”与“没全记对”的请求（1,304 个请求，18 个模型，按交付结果不做筛选）。

差距 24.03 点里 19.42 点来自“请求根本没提交”。原始计数中仍有 21 个完整经验的请求失败、458 个不完整经验的请求成功——完整存档既不必要也不充分（附录 C.1.2，描述性）。

没提交的原因两样：Oracle 68 个遗漏里 61 个已不够一次修正的预算；Filesystem 133 个遗漏全都还剩写入额度。例：Oracle T10 预算 17 单位，四处修正共 8，再读一次上下文（5）仍够，读第二次就交不齐；GPT-5.4 读了 3 次花掉 15 单位，只完成 1 处修正（附录 D.2）。

改变的判断

评估长期自改进，不能只看任务成功，也不能只看“有没有存”：修订、保留、使用是三个分开的瓶颈。维护上，变化后改得不全；执行上，记对了也可能因预算或调用顺序交不出来——两头都要单独测。

本项目读法：这是一份诊断基准，不是改进方法；它支持“分开计量”的必要性，不证明存档内容导致了任务分差距。

读之前先知道

  • 每个模型 × 环境 × 条件只跑一条任务流，没有重复种子；图中四分位带描述模型间差异，不是运行间不确定性。
  • 有 / 无经验两条流的环境状态会分叉；第 5 块的配对仍可能在目标、顺序、剩余预算、题内发现上不同，作者标为描述性分解。
  • 覆盖率对任务表现的关联在加入模型 / 任务固定效应和位置趋势后降到 0.149 / 0.096（附录 C.1.3），不能当作存档内容的因果效应。
  • 经验分由 LLM 评审按私有细则打；跨评审一致性高，只说明细则下稳定。参考版本含“代理尚未遇到”的内容，覆盖率不是存档内容的精确率。
  • RT 只记首次到齐，不看之后是否保持；DP 含变化首题内的适应。
  • 环境是代码模拟的 18 个应用；结论是这些环境与 Hermes harness 下的测量。
