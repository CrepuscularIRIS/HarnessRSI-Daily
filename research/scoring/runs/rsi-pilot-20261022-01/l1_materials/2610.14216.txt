[abstract]
Coding agents such as Claude Code also follow text files that developers write for them: a project file, skills the agent may choose to open, and rules that load automatically when the agent reads matching files. We call these files the agent's harness. Developers add to it whenever they correct the agent, but one success proves little: the same agent can pass a task once and fail it the next time. We present Cortex, a tool that tests changes to the harness instead of trusting them. It saves fixes from the developer's sessions as replayable tasks, finds the corrections that recur, writes one skill or rule at a time, and keeps it only if repeated runs with and without it show a net gain and no task made noticeably worse. Existing text is tested the same way before it is deleted, and Cortex neither adds nor deletes text the agent never used. We tested Cortex with Claude Haiku 4.5 on a repository built for the purpose, with conventions the model tends to break, one area with nothing to learn, and a script playing the developer. On held-out tasks, the harnesses it built made the agent follow the conventions far more often than no skills or rules did, left the comparison area unchanged, and added no text read on every turn. Rules, which load automatically, did most of the work; skills helped only when offered with the files a task touches, and those offered on every turn were rarely opened. Cortex kept none of the useless or harmful suggestions we planted, but the agent never opened the useless ones or the harmful skills, and it reached no verdict on the harmful rules, so the test shows that Cortex keeps no unused text, not that it detects damage. Under the stronger Claude Sonnet 5 a single run's harness added little, and on a real open-source project, where the agent was rarely corrected, Cortex found nothing to learn. We release the tool, the lab and its data.

Cortex: Measurement-Gated Evolution and Pruning

of Coding-Agent Skills and Rules

Samuele Giampieri

Affiliation:
Independent researcher

October 2026

Abstract

AI coding agents such as Claude Code do not act on their training alone; they also follow text
files that developers write for them. A project file describes how the code should be written,

skills
are short guides the agent may choose to read when it judges them relevant, and

rules
are notes tied to particular files, which the agent sees automatically whenever it
opens one of those files. We call these files the agent’s
harness
. Developers add to it
each time they have to correct the agent, but checking whether an addition really helps is
harder than it looks: the same agent given the same task can succeed once and fail the next
time, so seeing an instruction work once proves little.

We present Cortex, a tool that tests changes to the harness instead of trusting them. At the
end of a working session it saves any fix the session made as a task it can replay; across
sessions it spots the corrections the developer keeps making, and writes one new skill or rule
at a time to prevent them. It then runs the agent on those tasks several times with the new
text and several times without it, and keeps the text only if it helps overall and makes no
single task noticeably worse. Text already in the harness is tested the same way before it is
deleted. Throughout, Cortex records whether each piece of text reached the agent, and it
neither adds nor deletes text that the agent never used.

We tested Cortex with Claude Haiku 4.5 on a repository built for the purpose, with a few coding
conventions the model tends to break and one area with nothing to learn, kept as a comparison. A
script played the developer, and Cortex was run several times from scratch. Each harness it built
was then tested on new tasks it had never seen.

The harnesses Cortex built made the agent follow the conventions far more often than a harness
with no skills or rules, left the comparison area unchanged, and added no text that the agent
must read at every step. The clearest lesson is about how advice is delivered rather than what
it says: rules, which the agent sees automatically, did most of the work, while skills, which
the agent must choose to open, helped only when they were offered for the files a task touched;
offered on every turn, they were rarely opened. We also fed Cortex useless and harmful
suggestions on purpose. It kept none of them, but the agent never opened the useless ones or the
harmful skills, and the harmful rules, which did load, were tried on tasks that mostly failed
without them, where Cortex reached no verdict, even when a harmful rule broke a task that passed
without it. This shows that Cortex keeps no text the agent never uses, not yet that it can spot
text that does damage. Finally, in this study Cortex was worth as much as the model needed
correcting: under the stronger Claude Sonnet 5, which already followed most of the
conventions, a single run’s harness added little, and on a real open-source project where the
agent was rarely corrected, Cortex found nothing to learn. We release the tool, the evaluation
lab and the data behind every number in the paper.

Introduction

Coding agents are increasingly steered not only by their weights but by text their users
edit. A project instruction file (
CLAUDE.md
, or
AGENTS.md

[
16
]
),
a folder of
skills
the agent may choose to invoke, and
rules
that load when
the agent reads matching files
[
4
,

]
together make up
what this paper calls the agent’s
harness
: the part of its behaviour a developer
can change in a minute, by editing text. The agent works in
turns
: at each step the
model reads its
context
, the text in front of it (the harness text that is loaded,
the request and the work so far), and then acts. Harnesses grow the way documentation
grows. A correction a developer has to make twice becomes a line, the line stays, and
every line that is always in context is paid for on every turn of every session.

Little of it is measured. Whether an instruction helps is often judged the way it was
written: by someone who watched it work once. That is not evidence, because an agent’s
success on a fixed task is a noisy quantity: the model samples its output, so the same
agent can pass a task on one attempt and fail it on the next. Results in this paper are
therefore given as a
pass rate
, the share of attempts that succeeded, and
differences between pass rates in percentage
points
. In the evaluation reported
here, one and the same harness, measured twice on the same tasks in separate batches of
rollouts, differed by −3.3 points (95% confidence interval, or CI,
[−7.3, 0.0], resampling tasks;
Section

4
explains these intervals), a difference
that, seen once, would pass for an effect. Recent studies report that adding skills can
make an agent worse
[
54
]
, that skill gains measured on the tasks one
repository supplies could not be told apart from run-to-run
noise
[
26
]
, and that whether an updated harness helps depends on the
model that uses it: weaker models often fail to activate, or to follow, what was
added
[
31
]
. A harness curated by impression can accumulate
instructions that do nothing, some that hurt, and a context bill for all of them.

These systems are typically optimised and evaluated against benchmarks. A developer’s
problem is narrower and, in one respect, harder: one repository, its own conventions, a
handful of tasks drawn from their own work, a fixed context budget, and no way to tell
whether a given instruction earns its place.

We present
Cortex
, a tool for Claude Code that treats the harness as something
to measure rather than to curate (
Figure

1
). Cortex calls each skill or rule an

item
, and the harness the developer is using now the
live
harness. It
consists of three commands.
/harvest
runs at the end of a working session. When
something in the session went from broken to working, it saves a replayable

task
: the broken commit, the developer’s request, and a
check
, a script
that decides whether an attempt at the task succeeded. It also logs each correction the
developer made along the way.
/evolve
reads the corrections that recur and writes

one
new skill or rule, a
candidate
, for one of them. It also chooses the
candidate’s
loading tier
, which decides when its text enters the agent’s context
(
Section

2
): if the fixes behind the problem sit in one folder, the
candidate loads only when the agent works there. It then runs the agent on the
harvested tasks several times each, with the live harness and with the live harness plus
the candidate, in disposable clones of the repository. Each attempt is a
rollout
,
and a batch of rollouts that compares two harnesses in this way is a
sweep
. The
candidate is kept only if it helped,
fired
in at least one of its rollouts (a rule
loaded into the agent’s context, or a skill opened), and made no task worse beyond a set
tolerance, which is zero on a task the live harness never failed; a candidate killed only
for such a drop is swept again first.
/prune
works the other way round: it
re-measures live items by removing them one at a time, and never deletes one it has not
seen fire. One principle runs through both measurements:
an item is credited or
blamed only where it entered the agent’s context.
