arXiv: 2611.22017    title: SkillBuffBench: Measuring What Agent Skills Contribute across Harnesses, Models, Skill Access Modes and Memory

[abstract]
Agent Skills, file-based packages of procedural knowledge that a coding agent can discover and load on demand, are now shipped by every major agent harness, yet the evidence for how much they help comes almost entirely from settings in which the right Skill is hand-picked for the task and the agent starts from a blank slate. Neither holds in deployment, where an agent chooses from whatever library happens to be installed and frequently carries memory from earlier work. We present SkillBuffBench, a benchmark and paired evaluation protocol that treats Skill access as a three-level factor (no Skill, a curated Skill, and automatic invocation from an installed library), crosses it with memory (off and on), with four agent harnesses and with multiple models (the state-of-the-art proprietary models from Anthropic, Google and OpenAI, and the state-of-the-art open-weight models from Chinese providers), every model being run under every harness, and evaluates the result on research tasks contributed by domain experts together with the Skills they use, currently in materials science and biology, with the suite extended on a rolling basis. Every run is marked by a deterministic verifier; uncertainty is reported with a paired, task-level bootstrap; and cost, agent rounds and wall-clock time are reported alongside the score rather than folded into it. This version of the paper describes the design of the benchmark, its evaluation protocol and its current tasks and Skills. The evaluation is in progress: results will be added once the runs are complete, and the task suite, results and analysis will continue to be updated on a rolling basis.

Language-model agents are increasingly judged not by what the underlying model knows but by what the system around it lets the model do. A large part of that system is now written in plain files. An Agent Skill [ 2 ] is a directory containing a short description, a set of instructions and, optionally, scripts, templates and reference material; the agent harness —the program that runs the tool loop, manages the workspace and decides what enters the context window—advertises the descriptions of the installed Skills to the model and loads the body of one only when the model asks for it. The idea of giving an agent a reusable library of procedures is older than the format [ 34 ] , but the format has made such libraries cheap to write and easy to share. An agent in deployment now commonly runs with a library of Skills installed, most of them irrelevant to the task at hand. Whether those Skills help is an empirical question, and it has only recently been asked carefully. Benchmarks for agents now cover a wide range of work [ 38 ] : resolving software issues [ 16 , 9 ] , operating a terminal [ 22 ] , completing workplace and customer-service tasks through tools [ 31 , 37 , 5 ] , calling functions correctly [ 28 , 7 , 42 ] , browsing and research [ 23 , 8 ] , using a desktop [ 36 ] , planning [ 10 ] , and domain work in finance and civil engineering [ 6 , 20 ] . A parallel line measures what agents can do in cybersecurity, from capture-the-flag challenges to finding, exploiting and patching vulnerabilities in real codebases [ 40 , 39 , 35 , 30 , 41 ] , and another measures how long a task an agent can sustain [ 17 ] and whether it holds to its deployment policy under attack [ 43 , 11 ] . These benchmarks share a protocol: a sandboxed environment, a well-defined task, a deterministic check of the final state, and a comparison across models and, sometimes, across harnesses, tool sets or retrieval methods. What they hold constant is the procedural knowledge available to the agent. They vary the agent and fix its augmentation, and, to our knowledge, none treats persistent memory as an experimental variable. SkillsBench [ 19 ] inverted this, holding the task, model and harness fixed and varying only whether curated Skills are available. Across 87 tasks and 18 model–harness configurations it found that curated Skills raise the mean score by 16.6 percentage points, that the gain varies widely by domain and by harness, that 13 tasks get worse with Skills, and that Skills written by the model itself did not substitute for curated ones. That study establishes that Skills can matter. It leaves open three questions that decide whether they matter in use. Curated access is an upper bound, not a deployment condition. In a curated-Skill condition a person who knows the task has already solved the hardest part of the problem: deciding which knowledge is relevant. A deployed agent receives no such help. It sees the descriptions of every installed Skill, must recognise that one of them applies, must choose it over plausible distractors, and must then follow it. Each step can fail, and loading the wrong Skill can be worse than loading none. The gap between the right Skill, supplied and a library, searched is the quantity a practitioner needs, and it cannot be read off a curated-versus-none comparison. Memory is an uncontrolled second source of procedural knowledge. Modern harnesses persist information between sessions: project instructions, notes the agent wrote for itself, records of what worked last time. Memory and Skills overlap in function—both carry procedure into a fresh context—so an experiment that does not control memory cannot attribute an improvement to either. Worse, repeated trials of one task are no longer independent if the second trial can read what the first one learned. Whether a Skill still helps an agent that already remembers a successful attempt, and whether memory alone recovers the benefit of a Skill, are open questions. Model and harness effects are confounded. Skill discovery and loading are implemented by the harness, not the model, and harnesses implement them differently. Most existing evidence pairs each model with its vendor’s own harness, or varies the model inside a single harness, so a difference between two rows of a results table may be due to the model, the harness, or their interaction. Separating them requires running the same models under different harnesses. This paper introduces SkillBuffBench, a benchmark and evaluation protocol built to answer these three questions. Its design is a full factorial: three Skill conditions (none, curated, and automatic invocation from an installed library), two memory modes (off and on), four harnesses, and multiple models from different providers, each run under every harness, with every cell evaluated on the same tasks and repeated three times.
