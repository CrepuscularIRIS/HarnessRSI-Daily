arXiv: 2611.22299    title: Harnesses That Improve Themselves: A Unifying Framework for Self-Improving Agent Harnesses

[abstract]
Whether a foundation model succeeds as an autonomous agent depends as much on its runtime software as on its weights. This runtime, the agent harness, manages context and memory, steers multi-turn control, executes tool actions in sandboxes, and verifies work before stopping. Because models differ in how they use tools and how they fail, a static harness tuned for one model or task often stalls, wastes tokens, or regresses on another. This bottleneck has driven a shift from prompt tuning to self-improving agent harnesses: systems that inspect their own execution traces, separate runtime bugs from model limits, and rewrite their own code. We present a unifying architectural and design framework for self-improving agent harnesses. The framework pairs four editable runtime components (context and state, agent control, action interfaces, and verification and recovery) with a four-stage loop that diagnoses failures, proposes code patches, validates candidates, and deploys updates. Using this framework, we show how optimizers trace errors across long trajectories and discover reusable runtime mechanisms such as pre-stop verifiers, loop breakers, and persistent memory. We further show why full-harness rewrites overfit or break across modules, and how modular updates with validation gates generalize across models while bounding token cost. To keep self-modification safe, we establish practical defenses against recurring failure modes including prompt bloat, benchmark gaming, and evaluator tampering. Finally, experiments on SWE-bench Lite validate this framework, showing that gated modular evolution outperforms prompt reflection and full-harness rewrites across models and repositories at a fraction of the token cost.

Language models are now widely deployed as autonomous agents to resolve bugs in large software repositories [ 1 , 2 ] , run command-line tools [ 3 , 4 ] , operate desktop and web interfaces [ 5 ] , and execute multi-step reasoning and scientific workflows [ 6 ] . Every working agent pairs a foundation model with an agent harness : the stateful runtime software that turns single-step token prediction into sustained, multi-turn execution over long horizons. While the model supplies general reasoning and code generation, the harness governs the surrounding execution loop at every turn by assembling and compacting state history, scheduling control flow and subagent handoffs, executing tool or shell calls inside isolated sandboxes, and running automated test or recovery checks before task completion [ 7 , 4 , 8 ] . Why the harness matters as much as the model. Early work on language-model agents treated the runtime harness as thin engineering glue around a model checkpoint. Over time, its scope and responsibility have grown into a core part of any agentic system, and recent controlled evaluations across coding, terminal, and computer-use tasks highlight three reasons for this shift. First, the harness shapes how an agent fails and how much it costs to run. When the same model runs inside different production harnesses, its dominant failure modes (quitting before testing its work, looping on failed commands, overflowing its context window, or skipping verification) follow the design of the harness rather than the model family. Token usage per solved task can also vary by an order of magnitude across harnesses [ 9 , 10 ] . Second, a well-designed harness both supports weaker models on simple tasks and unlocks stronger models on complex ones. On short, self-contained problems, extra harness structure mainly compensates for gaps in weaker models. On long, repository-scale tasks, however, a capable harness does the opposite: its state tracking, multi-step planning, and verification hooks give strong models the scaffolding they need to solve problems they could not finish alone [ 11 ] . Third, no single static harness is optimal for every model. Because models differ in how they format tool calls, follow instructions, and balance exploration against action, a harness tuned for one model often underperforms or flips leaderboard rankings when paired with another [ 10 , 8 ] . Even when the base model is held fixed, longitudinal audits across dozens of human-maintained harness releases show that manual tuning frequently stalls or introduces regressions on earlier tasks [ 12 ] . From prompt pipelines to self-improving agent harnesses. Because harnesses have such a large impact on reliability and must match specific models, the way engineers build them has evolved through three distinct generations [ 8 , 4 ] . First, manual harness engineering relies on human developers to inspect failed rollouts by hand and craft better system prompts, Agent-Computer Interfaces (ACIs), context compactors, and retry loops, producing foundational runtimes such as SWE-agent [ 2 ] , Antigravity, Claude Code, Codex CLI, and Gemini CLI [ 4 , 7 , 12 ] . Second, automated prompt and workflow optimization introduced programmatic search over frozen models, tuning prompt instructions, demonstrations, and module parameters [ 13 , 14 ] , reflecting on multi-turn execution traces [ 15 , 16 ] , or searching over code-defined multi-agent workflows [ 17 , 18 ] . While these second-generation optimizers can inspect multi-turn traces or search over multi-agent routing topologies, they optimize prompts, parameters, or inter-agent call graphs while treating each agent’s inner stateful runtime harness (context compactors, sandboxed ACI tool wrappers, loop controllers, and pre-stop verification hooks) as fixed primitives rather than mutable software. Third, self-improving agent harnesses treat the executable code of the multi-turn runtime itself as mutable software. In external meta-harness search, an outer coding optimizer inspects multi-turn execution trajectories and patches the target agent’s context managers [ 19 , 20 ] , tool wrappers [ 21 , 22 ] , control loops [ 23 ] , and verification hooks [ 24 ] . In self-referential and recursive harnesses, the agent folds this optimization loop into itself, using its own model to diagnose recurring execution failures and patch its own runtime hooks [ 8 , 25 ] , or even rewriting its own improvement algorithm [ 26 , 27 , 28 ] to evolve open-ended coding agents [ 29 , 30 ] . To formalize this paradigm, we establish an architectural and engineering design framework for self-improving agent harnesses. While there is growing research interest in co-designing model weights and harness code together (§ VIII ), our focus in this paper is on harness self-evolution while the underlying model weights are held fixed. ## II The Agent Harness and the Self-Improvement Loop
How an agent harness connects the model to the environment. In a long-horizon task, a frozen foundation model cannot inspect a workspace, execute commands, or track multi-step state on its own. Instead, it operates inside an executable agent harness (such as Claude Code, Antigravity, Mini-SWE-Agent, or Terminus) that mediates interaction with the live environment across every turn (Fig. 1 , left) [ 4 , 8 ] . Unlike a static prompt template, the harness governs autonomous execution across dozens or hundreds of turns through four coupled, code-editable components. First, Context and State Management controls multi-turn history across the trajectory by assembling dynamic instructions, separating working memory from experiential memory [ 31 ] , and masking or compacting stale observations across prior turns so long horizons do not overflow context [ 32 , 33 ] . Second, Agent Control steers multi-turn exploration by regulating turn budgets, detecting and breaking repetitive loops, switching between planning and execution phases, and delegating subtasks to isolated subagents [ 8 , 25 ] . Third, the Action Interface defines how the agent acts upon the environment through an Agent-Computer Interface (ACI) [ 2 , 34 ] , translating model outputs into sandboxed shell commands [ 35 ] , file edits, or GUI actions while parsing or truncating single-turn raw stdout and UI state on the current step and loading tool schemas on demand [ 36 ] . Fourth, Verification and Recovery intercepts stop or state-commit signals from Agent Control to run automated test suites, linters, or visual checks, routing failures back into Context and State for self-repair before termination [ 37 , 38 , 39 ] . Fine-grained modular systems further split these four components into five modules (separating single-turn observation formatting from multi-turn context management [ 25 ] ) or four lifecycle contexts (plan, supervise, verify, recover [ 39 ] ), while pre-execution action guards bridge Component 3 and Component 4 [ 40 ] . The four-stage closed-loop self-improvement cycle. Because these four runtime components interact tightly across a trajectory, a flaw in one component quickly cascades into others. Self-improving harness frameworks replace manual debugging of these coupled components with an automated outer loop (Fig. 1 , right) that iteratively evolves the harness over successive rounds. In Stage 1 (Diagnose Failures), the system runs the current harness on a development split to collect multi-turn rollout trajectories, and localizes systematic harness bottlenecks by clustering verifier errors, diffing passing and failing trajectories, or searching raw execution logs [ 19 , 8 , 21 ] . In Stage 2 (Propose Edits), an optimizer translates these diagnostic findings into concrete code or hook patches across one or more harness components [ 25 , 22 ] . In Stage 3 (Validate and Filter), candidate harnesses are screened on validation tasks, trace-replay simulators, or efficiency frontiers to check runtime execution, prevent regressions, and filter out overfitted or token-wasteful edits [ 20 , 24 , 41 , 42 ] . Finally, in Stage 4 (Deploy or Route), a validated patch is either merged into the default harness for subsequent runs [ 19 , 8 ] , saved to an archive of harness variants that future search rounds can branch from [ 29 , 24 ] , or paired with a lightweight router or policy that selects a tailored harness configuration for each incoming task [ 43 , 44 ] . Key design choices in self-improving harnesses. Across this loop, existing systems differ along three practical design choices [ 45 , 8 ] . First, who proposes the edit: a same-model self-loop lets a capable coding agent diagnose and patch its own harness without maintaining a second model [ 8 ] , whereas an external coding optimizer is required when the task agent is small or domain-specific (§ V ) [ 19 , 21 , 39 , 46 ] . Second, what code can be modified: restricting edits to the task harness keeps search predictable, whereas allowing recursive edits to the optimizer itself can unlock better search tools at higher compute cost (§ IV ) [ 26 , 27 , 28 , 29 , 30 ] . Third, where the evaluator resides: grading scripts and logs should always be locked in read-only storage outside the agent sandbox so the optimizer cannot pass tests by modifying the evaluator or fabricating logs (§ VI ) [ 47 , 48 ] .
