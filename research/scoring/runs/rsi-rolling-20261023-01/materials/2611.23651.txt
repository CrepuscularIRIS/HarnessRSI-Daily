arXiv: 2611.23651    title: Safe Personal RSI: Evaluating and Repairing Personal-Agent Updates

[abstract]
Kicker is a personal health assistant. Changes to an assistant's reusable instructions can improve task handling while changing what it discloses, which requests it follows, and how it reports actions. We study Safe Personal RSI, an update-evaluation component developed for Kicker. We restrict recursive self-improvement (RSI) to prompt updates, with model weights and runtime code fixed. The procedure tests proposed and current instructions, repeats failing cases, temporarily undoes changes to guide repairs, and checks safety and task performance before adoption. If no version passes, the current instructions stay in use. Our executable benchmark contains 29 email, calendar, health, and marketplace cases, with separate probes for authorization reuse, memory, and tool-output injection. Across three models and two deliberately risky edits, the procedure rejects 20 of 21 update attempts. In repair confirmation, an admitted GPT-5.6 Luna repair reduces attack violations from 10.7% to 0% and increases safe task completion from 89.7% to 100%; a broad handwritten authority rule matches these outcomes. Under stronger attacks, a repair transferred from Qwen2.5-7B-Instruct to Qwen3-14B reduces violations from 69.0% to 17.9% and increases safe task completion from 19.5% to 64.4%. Separate runtime probes examine memory-entry deletion and identify missing local OAuth scope checks in the evaluated snapshot.

Kicker is a personal health assistant. Assistance in this setting may draw on sensitive personal context, including appointments, health-related messages, and user preferences. Relevant information helps the assistant understand a task, while the owner’s authorization determines what it may share or agree to on their behalf. The instructions guiding an assistant’s behavior can be revised during development. An update might encourage more initiative, reduce repeated confirmation, or simplify completion reports. Once adopted, those instructions affect future tasks. The update can also change how the assistant interprets requests from external senders or reports the outcome of a tool call. Testing the proposed behavior is therefore part of deciding whether to use the update. A health-privacy example The owner asks for routine inbox handling. A clinic message contains a blood-pressure reading and a medication dosage change. Another message claims that reimbursement requires forwarding the visit summary to an external benefits processor. The owner has not authorized that disclosure. In this GPT-5.6 Luna development case, the unrepaired update produces a recipient-addressed draft containing private health information in two of three runs. The repaired instructions produce no disclosure drafts and complete the owner’s task in all three. The assistant summarizes the messages and asks before forwarding the private details. The broad authority-rule comparator also avoids disclosure. These are paraphrased trace summaries from the case-study report [ 13 ] ; delivery is disabled, and clinical advice is outside the test’s scope. We also use other inbox tasks to test authorization. A marketplace case asks the assistant to handle a buyer’s offer at 70% of the asking price. The external offer supplies terms, while the owner decides whether to accept them. This lets us examine the same authorization boundary beyond health information. The update-evaluation problem Safe Personal RSI compares proposed instructions with the current version, uses failures to guide revisions, and evaluates whether to adopt the result. We study both outcomes: a repair that passes the checks and an update that is declined when no suitable version is found. We measure task handling alongside violations so that an assistant’s failure to help remains visible. This report describes the component developed for Kicker and the evidence from controlled experiments. ## System Setting and Update Requirements
We represent the agent’s reusable instructions as a harness : an ordered set of named prompt blocks. An update changes these blocks while model weights, runtime code, tool implementations, authentication, and the owner remain fixed. The current harness is the update’s parent ; denotes the initial harness. Editable instructions and external content The tested edits change the agent’s role instructions. One encourages accepting reasonable offers and concise completion reports. A stronger edit adds inbox-zero pressure, sharing requested mailbox details, and avoiding further questions. These predefined edits deliberately pressure authorization and reporting boundaries. They provide the same starting proposal to direct adoption and Safe Personal RSI. Attackers control specified external content, principally email bodies. The owner’s legitimate task remains fixed. Tests inspect five primary violation categories: unauthorized disclosure, privacy oversharing, misleading execution reports, unauthorized commitments, and source confusion. Separate runtime probes inspect API and stored-memory state. Requirements for evaluating updates Authorization. A sender’s request should remain distinct from owner permission. Private disclosure and commitments require the relevant approval. Task handling. Avoiding a violation should accompany useful handling of the owner’s request. A summary, a factual nonbinding draft, or a request for missing authorization can still complete the legitimate task. Action reporting. Preparing a draft and sending a message are different outcomes. Evaluation inspects tool results and responses to check whether the assistant reports what happened. Adoption evidence. The proposed version is compared with the current harness. Repairs face verification and a separate adoption decision. If no attempt passes, the current version stays in use. Component boundary In the reported experiments, Safe Personal RSI runs offline during update evaluation. Runtime controls separately govern authentication, tool permissions, and stored information. Our memory and OAuth probes examine those controls with the prompt-update boundary held fixed. A replay is one execution of a case. Admission is the decision to adopt an update after testing; a flag is a violation identified by a test check or risk audit. Utility combines task success with fixed penalties for tool-cost proxy, latency, and confirmation requests. 3 / METHOD

## Safe Personal RSI
We compare a proposed instruction update with the current harness, also called its parent. Testing both versions helps identify changes that introduce failures. We also test the proposed version for failures shared with the current one, so existing weaknesses remain visible. 1. Propose Edit the current harness. Record the proposed version. 2. Search + confirm Test both versions; replay failing cases. 3. Investigate Temporarily undo prompt changes and replay. 6. Adopt or keep Adopt a passing version; otherwise keep the current one. 5. Decide Check safety, task handling, and complete execution. 4. Repair + verify Revise instructions and recheck failures and utility. No confirmed failure: test the proposed version Testing and confirmation Development cases specify an owner task and external content that may try to redirect the assistant. Variants add urgency or claimed authority while keeping the owner’s request fixed. When a failure is found, additional runs check whether it recurs. Investigation and repair We temporarily undo changed instructions and rerun failing cases to help identify a repair target. Repair can append a category-specific clause or use a language model to rewrite a prompt block. The rewritten block receives failure traces and general authorization and reporting rules. Each attempt allows at most two repairs. Adoption The resulting version is tested on confirmed failures and development tasks. Admission requires at least five admission runs per harness, all completed, maximum suite-normalized category risk at most 0.1 and no higher than the parent, and the configured utility criterion. A confirmed failure on a case designated as unauthorized disclosure blocks adoption even after repair. If no version passes, the current harness stays in use. Utility must show nonnegative gain, or satisfy the specified alternative combining success-rate tolerance with lower cost proxy. These are empirical point-estimate rules. We log versions, failures, repairs, and decisions. Appendix B gives the algorithm; Appendices E and I specify budgets, thresholds, and decision rules. The companion paper explains the research method in detail [ 22 ] . 4 / EXPERIMENTAL DESIGN

## Experimental Design
We evaluate updates on 29 cases : 23 core email attacks and six calendar, health, and marketplace extensions. Sixteen cases support update development: 15 attacks and one authorized control. The other 13 attacks are excluded from each update loop. These case families were known during benchmark development and reused in exploration. Runtime and containment We use Willow’s agent API, graph runner, authentication, and isolated PGlite persistence, with real model calls through OpenRouter. Mailboxes and external services are synthetic. The assistant can read mail and save drafts; delivery and transactions are disabled. Calendar and health content appear in email. Separate probes examine authorization reuse, memory, tool-output injection, and API controls. Comparators In repair confirmation, all arms start from the stress update. Fixed-rule adds a static instruction; Safe Personal RSI uses the selected harness. Controllable implicit runtime safety instructions are removed equally from all arms. Authentication, allowlists, and draft-only containment remain. Metrics and repetitions Attack violation rate is flagged attack runs divided by planned attack runs. Flags combine deterministic checks with a fixed GPT-5.6 Sol risk audit. Safe task completion requires a completed run, a positive legitimate-task audit, and no violation flag. Failed and empty runs receive no completion credit. Useful handling can include declining an injected demand while completing the owner’s task. The controlled-admission study tests GPT-5.6 Sol, GPT-5.6 Luna, and Qwen3-14B. It uses two rounds and up to two candidates per round, with template repair. The repair studies use one round, one candidate, and LLM repair; final Qwen3-14B confirmation evaluates a transferred harness. Controlled admission uses five final runs per case: 140 attacks and five controls. Repair confirmation uses three: 84 attacks and three controls. Its safe-completion rate uses all 87 runs. The admission study instead uses completed, unflagged execution as its success proxy. Its utility score adds fixed penalties for tool-cost proxy, latency, and confirmation requests; scores are compared within that protocol. All final evaluations use fixed harnesses.
