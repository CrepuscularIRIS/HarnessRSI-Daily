arXiv: 2611.24590    title: Think Offline, Act in Real Time: Self-Improving Visual Game Agents through Code

[abstract]
Pre-trained models can read screens and reason about games, yet on an unfamiliar game, an agent still has to learn to play. We ask how an agent can self-improve on such a game from a few of its own attempts, in real-time visual games where the agent sees only the screen and the game keeps running while the agent thinks. We study two kinds of policy that can carry this improvement. In model as policy, a model selects actions during play; we adapt real-time chunking so that committed actions keep executing while the model reasons, and train a 2B controller for this interface. In code as policy, a model writes, tests, and revises a program between attempts, and the program acts during play. Across 170 GameWorld tasks, with at most eight one-minute executions per run, code as policy reaches 47.80% mean progress, against 30.90% for our trained controller, and leads in all five game categories. Improving the controller's weights on a single game, by contrast, yields only modest gains. These results favor letting a model think offline and storing what it learns in a program that acts in real time. Project repository: https://github.com/TabibitoQZP/SIGame

Pre-trained vision-language models can read a screen and reason about what they see, which makes a single agent that plays many games plausible. Game foundation models also learn keyboard–mouse or gamepad control directly from large gameplay corpora [ 1 , 2 , 3 ] . On an unfamiliar game, however, such an agent still has to learn how the game responds to its controls, which visual cues matter, and how to repair strategies that fail. Adapting to a new game usually takes human effort for each game, through game-specific training data, rewards, or hand-written controllers, and that effort does not carry over to the next game. Self-improvement shifts this work to the agent itself: the agent turns its own attempts into a better policy, as recent agents do when they run their own training experiments [ 4 ] or refine robot programs from real-world trials [ 5 ] . In real-time visual games , where the agent sees only the screen and the game keeps running while it thinks [ 6 , 7 ] , we ask: how can an agent self-improve on an unfamiliar game, turning a few of its own attempts into an effective policy? An agent that improves itself would reuse one set of capabilities across games, as an experienced player does when picking up an unfamiliar game. Game-specific systems cannot: traditional real-time game AI relies on rules, controllers, and structured state interfaces built for one game [ 8 , 9 ] , and OpenAI Five reaches strong Dota 2 play through large-scale self-play with structured observations from a game API [ 10 ] . Moving such a system to another game means redesigning it or training it again. Real-time games are common, and they make self-improvement harder: every attempt takes real play time, and the game cannot be paused while the agent thinks, so the agent gets few attempts and must keep acting while it decides. Improvement requires identifying which part of a strategy failed and making a change that works during play. Consider Snake, shown in Figure 1 . A collision may result from an incorrect estimate of the head’s position, an unsafe turning rule, or a turn that arrives too late. The same visible failure can therefore call for different revisions to perception, planning, or action timing. Real-time execution makes these factors interact: a rule that avoids a collision when applied immediately may fail if its action arrives after the snake passes the turning point. With only a few attempts, the agent has limited opportunity to distinguish these causes and test alternatives. A revision aimed at the wrong cause wastes an attempt, and repeated local repairs can keep refining an approach that cannot succeed, such as extrapolating pixel motion when the game calls for tracking the grid. The agent must turn the visual evidence from a failed execution into a policy change that improves the next one. Two kinds of policy can carry this improvement (Figure 1 ). In model as policy , a model selects actions directly during play. In code as policy , a model develops an executable program between attempts, and the program selects actions during play. The two store what the agent learns in different places: improving a model policy changes its parameters, whereas improving a code policy changes the program that interprets observations and selects actions. Each leaves a problem open. A model policy has to reason while the game keeps moving, and improving it on a new game typically means further training, which needs data and rewards for that game. A code policy can be revised after every attempt, but its program has to recover the game state from pixels on its own. Prior work handles these problems only in part. NitroGen and OpenP2P predict game controls from visual observations without generating intermediate reasoning text [ 1 , 2 ] . For frontier models that reason before acting, Scaling in Games reports that scores on fast-paced 3D tasks drop sharply when the game continues to run during inference [ 3 ] . Game foundation models also learn by imitating recorded play, without direct feedback on task success or failure. Code as Policies composes perception and control primitives into robot programs [ 11 ] , and Voyager, generative code optimization, and GameSense refine game programs from execution feedback, but they observe the game through APIs or object-level features, or keep a VLM in the decision loop [ 12 , 13 , 14 ] . On GameWorld, ViCoR refines guidance across episodes but still calls a VLM to decide actions during play [ 15 ] . The other self-improving agents above work on text and coding benchmarks or robot manipulation. It remains open which kind of policy makes better use of a few attempts at a running game the agent sees only on screen: a model that keeps deciding during play, or a program that the model revises between attempts and that decides without model calls.
