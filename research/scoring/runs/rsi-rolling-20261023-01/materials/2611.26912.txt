arXiv: 2611.26912    title: Self-Evolving Beyond Human-Crafted Experience for EDA Scripting

[abstract]
The growing complexity of electronic systems demands efficient design flows, yet EDA scripting remains a bottleneck: proprietary APIs are sparsely documented, and errors often appear as silent failures or cryptic exceptions. Hand-crafted knowledge helps but is difficult to maintain as toolchains evolve. We present ZhuLong-SE (Self-Evolution), an execution-grounded LLM agent that learns reusable knowledge from prior task traces. Building on ZhuLong, it enhances the task-level harness with API retrieval, documentation responses, isolated sandbox execution, and static checking, then adds governed cross-task self-evolution. Beyond solving individual tasks, ZhuLong-SE distills past execution traces into a three-tier memory store governed by ground-truth anchoring, disconfirmation filtering, held-out rollback, and anti-leakage retrieval. On the 158-task EDA-Eval-PyAether benchmark, the full task-level harness, with self-evolution disabled, achieves 92.4% pass@1 and outperforms ZhuLong on all five tested LLM backbones. On a harder instance-disjoint test set, self-evolution from the bare configuration surpasses a human-crafted-experience baseline by 2.5 percentage points (80.0% vs. 77.5% pass@1).

[intro/head from cached fulltext]
EDA scripting is challenging because tool APIs are tool-specific, sparsely documented, and exposed through SWIG bindings whose type rules differ from native Python. ZhuLong [ 1 ] is the first work that established an execution-grounded LLM agent for EDA scripting that combines API retrieval, documentation inspection, and sandbox execution via unified MCP tools, augmented by an offline API self-exploration mechanism that infers undocumented API behaviors through counterfactual experimentation. On the EDA-Eval-PyAether benchmark, the system achieved 78.5% pass@1, substantially outperforming a pure LLM baseline of 23.6%. However, a critical limitation remained: the agent solved each task independently and did not learn from past execution traces, so its performance on new tasks did not improve over time. Building on this task-level substrate, we introduce self-evolution : an offline system that distills execution traces into reusable knowledge and re-injects it into future tasks, with reliability gates that prevent unverified experience from misleading the agent. To provide reliable signals for self-evolution, we introduce a precision-optimized static checker for deterministic API misuse. It raises no error flags on the 158 benchmark ground-truth solutions, a sanity check limited to this reference-code set. Applying self-evolution to EDA scripting introduces two challenges. First, feedback is very sparse : the agent receives only a binary pass/fail from the hidden verifier. This is different from methods like SkillOpt [ 2 ] , which assume dense per-step rewards. Without careful verification, distilled experience can mislead. Second, instance-disjoint evaluation risks cross-split answer copying: a held-out task may copy a training sibling’s verbatim solution rather than transferring the underlying method, a problem recently observed in EvolveMem [ 3 ] . We present ZhuLong-SE (Self-Evolution) , which extends the ZhuLong task-level substrate with enhanced API retrieval and documentation responses, improved sandbox isolation, and precision-optimized static checking, and then adds a self-evolution layer with reliability gating. To handle sparse feedback, we introduce ground-truth anchoring, scope-boundary reflection, disconfirmation-based filtering, and a held-out validation loop that rejects degrading rounds. Beyond post-hoc evaluation gating, we design structural anti-leakage retrieval via names-only injection and deterministic docstring generalization to reduce the risk of cross-split answer copying. These mechanisms are designed to provide methodological signals without injecting full call sequences, while an evolution round is retained only when held-out validation does not degrade beyond the acceptance threshold. On the held-out test set, this design achieves a higher mean pass@1 than the human-crafted-experience baseline. Our contributions are as follows. • Self-evolution as a design methodology for EDA automation. We establish self-evolution—distilling execution traces into reusable knowledge and re-injecting them into future tasks—as a systematic methodology for system-level EDA scripting. To make it deployable under EDA’s sparse feedback and opaque commercial APIs, we introduce three governance rules: ground-truth anchoring, on-demand pitfall retrieval, and validation-gated rollback. • A rigorous evaluation protocol against cross-split leakage. We expose cross-split answer copying as a threat to trustworthy self-evolution evaluation, and propose a retrieval-time defense (names-only injection + docstring generalization) that removes full call sequences and task-specific details while preserving methodological transfer—establishing a protocol for future work on self-evolving design agents. • Counterintuitive design insights from controlled ablation. Controlled ablations on the 158-task EDA benchmark yield three observations: ground-truth anchoring prevents 12 of 24 failed-task traces from producing falsely verified entries; pitfall pre-injection reduces validation pass@1 by 8.0 pp in our ablation; and names-only retrieval improves over full-sequence injection by 4.7 pp. On the 40-task held-out test set, self-evolution from the Bare configuration reaches 80.0% mean pass@1, compared with 77.5% for the human-crafted-experience baseline, grounding these observations for future system-level design automation.

## III Method
Building on the origin ZhuLong execution harness [ 1 ] , ZhuLong-SE retains its retrieval–documentation–execution loop and introduces the blue-highlighted extensions in Figure 1 : enhanced API retrieval and documentation, isolated parallel sandbox management, a precision-optimized static checker, human-crafted rules and skills, and an offline cross-task self-evolution system. We describe the task-level harness extensions in Sections III-A – III-E , followed by self-evolution in Section IV . III-A API Retrieval ZhuLong provides a single search_apis MCP tool that uses semantic retrieval [ 1 ] . ZhuLong-SE retains its embedding-based semantic path, adds a dedicated keyword-oriented tool ( search_apis_by_keyword ), and supplements matches missed by the summary with a BM25 pass over the full description text. The keyword path targets queries that the semantic index handles poorly, such as abbreviations and camel-case fragments. The index tokenizes each API name by splitting on camel-case boundaries and stripping family prefixes. The query is bidirectionally expanded for abbreviations (e.g., CV CellView, crt create), enabling matches on abbreviated tokens inside API names. Depending on query type, a router expands abbreviations, returns direct-match hints for API-name fragments, or appends semantic results for natural-language queries. Finally, a cross-family synonym map links four functionally equivalent API families (db*, emy*, goa*, ae*), so a hit in one family surfaces equivalents in the others, addressing the failure mode where an agent recalls the correct operation but selects the wrong interface family. III-B Documentation Enrichment ZhuLong’s get_api_details returns parameter types, return values, examples, and inferred constraints [ 1 ] , but its per-API pages do not expose class instance properties. ZhuLong-SE therefore parses the raw documentation into a property table and appends it to each detailed response, so a queried class exposes its instance attributes alongside its methods. Constructor notes also disambiguate ambiguous calls: for example, emyPointArray accepts a plain list of points, a fact the per-signature page does not state. III-C Sandbox Execution We run multiple isolated sandbox endpoints, each with an independent working directory, and dispatch requests through a queue pool. A routine clears working directories before each run and resets library files to minimal content, so prior runs do not bias subsequent ones. This isolation ensures that execution feedback reflects the current code under test, not residual state from earlier tasks. The queue pool enables concurrent evaluation without changing ZhuLong’s per-task interaction protocol [ 1 ] . III-D Static Checking Because PyAether’s SWIG bindings expose all symbols at import time regardless of whether the underlying function exists at runtime, an agent may call a fabricated API or pass a native Python value where a SWIG-wrapped type is required without triggering any runtime error during self-test—yet the submission fails the hidden test that exercises that path. To catch such failures before submission, we introduce a static checker that runs after the agent’s self-test and before final submission. The checker parses submitted code into an abstract syntax tree, extracts API calls, and checks four documented misuse patterns: (i) fabricated APIs, (ii) incorrect keyword arguments, (iii) native Python values passed where explicit SWIG-wrapped construction is required, and (iv) silently swallowed exceptions. Actionable findings are returned to the agent for repair before final submission. The rules are derived from the API documentation and refined on real submissions. As a reference-code sanity check, the checker raises no flags on any of the 158 ground-truth solutions. This result is limited to that set and is not a general zero-false-positive guarantee. III-E Human-Crafted Experience ZhuLong-SE additionally injects four skills and one rule file authored from PyAether development experience rather than specific benchmark solutions. The skills cover API search, command-family selection, interpretation of silent or ambiguous sandbox feedback, and explicit SWIG type construction. The rule file requires API-detail checks before use, post-creation verification, and bounded search, providing a stable prior that complements knowledge learned from the execution traces.

## IV Self-Evolution
Unlike ZhuLong’s offline API self-exploration, which augments per-API documentation through counterfactual sandboxing [ 1 ] , ZhuLong-SE adds a cross-task offline self-evolution system (the blue-highlighted block at right in Figure 1 ). It distills task execution traces into reusable knowledge and re-injects it into later tasks. Knowledge is organized in three tiers, following the episodic-semantic-procedural memory distinction [ 20 ] : L0 holds raw traces, L1 stores aggregated patterns, and L2 archives distilled skill versions. Within L1, patterns are partitioned into four layers: solution (verified API routes), pitfall (negative warnings), meta (effective query patterns), and strategy (decision records). The write side runs offline after each training batch, and the read side injects knowledge at task formatting and on demand when the agent hits an error. The write, promotion, and round-acceptance stages apply reliability gates, as unvalidated experience can mislead [ 18 , 2 ] . Distillation and state updates run offline. During inference, the accepted memory is queried locally, without additional evolution or distillation. IV-A Distillation and Reflection The write side routes each task to the appropriate reflection path. We override the agent’s self-reported success with the evaluator’s binary verdict before any reflection begins, following Reflexion’s observation that reliable feedback is necessary for reflection to help rather than harm [ 31 ] . Tasks that still error on their final attempt take the error path ; tasks whose self-test passed but the evaluator failed take the contradiction path instead. This distinction is critical because a self-test-passed task’s error log contains only stale errors; mining pitfalls from these would record already-solved bugs rather than genuine gaps in the agent’s knowledge. Each L1 entry carries a reliability tier: verified , unverified , or pitfall . IV-B Knowledge Lifecycle with Reliability Gating Extracted L1 patterns undergo aggregation, gating, aging, and promotion to rules and skills. A verified entry is disconfirmed only when a failed task is an API misuse precisely attributed to that entry; at a count of two or more, the entry is filtered out. Unverified traces cannot downgrade verified entries, and entries not re-confirmed for five rounds drop to unverified. Promotion is guarded by a four-dimensional judge (abstraction, reusability, actionability, faithfulness) following SkillOS [ 24 ] , and a MUSE-style create-evaluate-refine loop [ 29 ] for low-scoring candidates. We add a zero-exception generality gate that rejects rules whose always/never statements do not hold across the entire API surface, ensuring that distilled rules remain broadly applicable rather than overfitting to specific task patterns. IV-C Anti-Leakage Retrieval Under an instance-disjoint split, naive retrieval risks cross-split answer copying. We prevent this through three mechanisms. Names-only pre-injection reduces a solution entry to API names only, dropping call order and parameters. Deterministic docstring generalization strips task-identifying specifics from both distillation and query sides. Problem-side embedding matches on problem similarity while returning solution metadata only at read time. Pitfalls are not pre-injected; they enter through on-demand runtime queries keyed to the agent’s actual error. IV-D Held-Out Gated Evolution After each training round, the agent generates on validation tasks (which never carry distillation). The round’s full evolved state is accepted only if the validation pass rate does not regress by more than 5 pp against the previous round. Otherwise, it is rolled back. This extends SkillOpt’s held-out criterion [ 2 ] from a single document to the entire evolved state.
