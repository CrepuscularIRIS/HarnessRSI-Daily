arXiv: 2611.33519    title: PRECEPT: Security Self-Improvement of Coding Agents via Evolving Principles

[abstract]
AI coding agents increasingly write and submit code with limited human review, and much of it passes functional tests while remaining insecure. We show that these failures persist. Across 14 task sequences, Codex, Claude Code, and Qwen Code fixed a vulnerability 85.7% of the time when shown the failing security test, then reintroduced the same vulnerability class in a new session 26.7% of the time, about as often as agents that had never seen it (27.5%). The capability is present; the retention is not. Neither recording the repair in the agent's persistent context nor supplying published secure coding principles closed the gap: the recorded fix stayed tied to the family of the task it came from, and the principles, written for human developers, remained too general to apply to the code at hand. The knowledge exists; it is not activated. We call the missing ability security self-improvement: an agent learns from its own security failures so that each lesson persists across sessions, applies to new code, and does not break what works. We present PRECEPT, which equips coding agents with this ability through an evolving library that starts from authoritative secure coding principles and revises them against the agent's own failures, so that each principle comes to fire on the code where that agent actually goes wrong. A revision is kept only if fresh executions show it makes code more secure while keeping functional success within a small tolerance of the agent without the library. Improvement continues across evolution steps rather than saturating after the first. On task families never seen during evolution, PRECEPT's weakest agent reaches 97.1% secure working code, above the strongest unaided agent at 81.9% and the strongest baseline at 87.7%.

AI coding agents are changing how software is developed. Given a feature request, an agent can explore a repository, modify its files, run the tests, and open a pull request on its own [ 1 ] . On GitHub, the share of pull requests that began with an agent’s first draft rose from 17% to more than 40% between March and September 2026 [ 2 ] . The code these agents write, however, often works but is not secure. On real-world feature requests, SWE-agent with Claude 4 Sonnet produced functionally correct code for 57% of the tasks but correct and secure code for only 11.8% [ 3 ] , and on C/C++ tasks, the best agent evaluated did so for only 23.8% [ 4 ] . These vulnerabilities arise without any attacker, and 58.2% of agent-authored pull requests in popular GitHub repositories received no explicit review [ 5 ] . As developers write and closely review less of the code, its security increasingly depends on the agent that writes it. What makes this more than a per-task quality problem is that the failures persist . We construct 14 task sequences in which an agent writes code that works but fails its security tests, is shown the failing tests and fixes the code, and later meets, in a new session, another task with the same type of vulnerability, as classified by the Common Weakness Enumeration (CWE) [ 6 ] (§ II ). Codex, Claude Code, and Qwen Code fixed the code in 85.7% of cases, yet on the later task they reintroduced the same CWE in 26.7% of executions, compared with 27.5% for a baseline of agents that had never been shown the earlier failure. We call this vulnerability recurrence . It is a failure of retention rather than of capability, because when the fix stayed in context, recurrence on a variant of the fixed task fell from 36.7% to 13.9%. Left to themselves, these agents did not learn from their security failures. A developer whose vulnerability is pointed out in review is expected to avoid it in later work, but an autonomous workflow may have no such developer, so the agent itself must keep the lesson. Two remedies are available to an agent, and neither prevents recurrence on its own. The first is the agent’s persistent context, the instruction files and memories that it reads in every session. In our study (§ II ), no agent recorded a fix there on its own, and the notes the agents wrote when asked often described the specific task they had fixed rather than a general lesson, so they helped on variants of that task but much less on other tasks with the same CWE. The second is published secure coding principles, which codify the knowledge needed to avoid these vulnerabilities [ 7 , 8 , 9 , 10 , 11 ] . Written for human developers, they state what should hold in general and leave it to the reader to decide where it applies. Given to the agents, neither the complete set nor only the relevant principles measurably lowered recurrence, whereas the relevant principle restated for the class of code at hand did, suggesting that the knowledge was available but not applied where the agents failed. Both findings point to the same need. A coding agent must learn from its own security failures , which reveal where its knowledge is not retained or not applied. Prior work makes AI-generated code more secure by training or steering the model, constraining its decoding, or retrieving security knowledge for each task [ 12 , 13 , 14 , 15 , 16 , 17 ] , but the security knowledge these methods rely on does not change with what the agent gets wrong. AI agents have been shown to learn from their own experience, revising their memories, skills, workflows, contexts, or rules [ 18 , 19 , 20 , 21 , 22 , 23 ] , and work on recursive self-improvement (RSI) has agents repeatedly improve their own code [ 24 , 25 , 26 ] or specifications [ 27 ] . These methods learn toward task success or efficiency, and under that objective a vulnerability rarely counts as a failure, because vulnerable code passes its functional tests. Coding agents need an analogous ability for the security of the code they write. We call it security self-improvement , in which a coding agent learns from its own security failures so that each lesson persists across sessions, applies to new code, and does not break what works. Security self-improvement can take different forms, and we pursue it through secure coding principles [ 7 ] . Our study found that a published principle became measurably helpful once restated for a class of code, so learning can start from the published principles and evolve them from the agent’s security failures. Principles also suit the requirements of security self-improvement. Kept in project instructions, principles remain available across sessions without changing model weights. Because they describe a class of code, their lessons can apply to new code beyond an individual fix. ## II Motivating Study
This study examines whether coding agents learn from their security failures and, if they do not, whether the remedies available to them close the gap. We follow each failure forward in time. After an agent fixes a vulnerability, we observe whether it avoids vulnerabilities of the same CWE on later tasks, with and without these remedies. II-A Research Questions • RQ1 (Recurrence): After fixing a vulnerability, do coding agents introduce the same type of vulnerability again on later tasks? • RQ2 (Capability vs. retention): Is recurrence a failure of security capability or a failure of retention? • RQ3 (Sufficiency of persistent context): Does carrying what an agent learned from an earlier failure into later sessions prevent recurrence? • RQ4 (Sufficiency of published principles): Does supplying published secure coding principles, either a complete set or only those relevant, prevent recurrence? II-B Study Design Sessions and persistent context. A session is one conversation with a coding agent and may span several tasks. An execution is the agent’s work on one task, a sequence of turns , each one a model call and the tool calls it makes. What carries over to the next session is the agent’s persistent context , its instruction files, such as AGENTS.md [ 30 ] or CLAUDE.md [ 31 ] , and its memory. Agents and tasks. We study Codex, Claude Code, and Qwen Code, all running on the same underlying model, Qwen3.6 (§ V-A ), on Python tasks from SeCodePLT [ 29 ] . Each task targets one CWE and comes with functional and security tests, and we count a vulnerability only when the security tests detect it. SeCodePLT writes each coding problem in several variants, and we call the variants of one problem a task family . Chains. Each task sequence, or chain , starts from a task on which all three agents wrote functional but insecure code. Each agent is shown its failing security tests, with no vulnerability named, and asked to fix its code, and the chain continues only if the fix passes both kinds of tests. The agent then works on tasks with other CWEs and then meets two later tasks with the same CWE as , one from ’s task family and one from a different family. We take the chains from task families held out from training, choosing as the tasks that all three agents failed most often, at most two per CWE. This gives 14 chains over 12 of SeCodePLT’s 17 CWEs. A chain needs a starting task on which every agent introduces the vulnerability, so that each has something to fix. For the other five CWEs, no held-out task qualified: on each, at least one agent wrote secure code or code that did not work. Conditions. The agent meets (1) with no earlier failure and fix ( baseline ); (2) in a new session, which carries over only its persistent context, so it recalls the fix only if it saved it ( new session ); (3) in the session that continues the conversation of the fix ( same session ); or (4) in a new session after writing what it learned into its instruction file when asked ( own note ). A preliminary study of 135 fixes with adds a verbatim record , the failed code and its fix pasted into the next session’s task prompt (Appendix B ). Published principles. We also execute each in a new session without an earlier fix, with guidance , text given to the agent to shape the code it writes, added to its prompt at six levels of specificity (Table XII in Appendix B ): (a) a one-line security reminder [ 3 ] ; (b) all 218 principles of the OWASP Secure Coding Practices [ 7 ] ; (c) the principles relevant to ’s CWE, which we select by hand as an oracle retrieval; (d) the relevant principle restated for the class of code, naming where it applies and what must hold without naming the task; (e) guidance written for itself, which says what its code must check without describing the reference fix; (f) a description of what the benchmark’s reference fix does. Measurement. Every later task is executed five times per condition and is compared with the baseline, paired by task, with 95% bootstrap intervals over chains. II-C Metrics Let when an execution of task introduces the vulnerability, that is, when its code passes the functional tests but fails the security tests. • (BIR) Baseline incidence rate. in the baseline, how often the agent introduces the vulnerability without an earlier fix. • (RR) Recurrence rate. , how often the agent introduces the vulnerability again after fixing it. • (RG) Retention gain. , how much less often the vulnerability appears because of the earlier fix. It is 0 when the fix leaves no trace and equals BIR when the vulnerability never returns. • (FR) Fix rate. The share of executions at that fix the vulnerability without losing functional correctness. It shows whether the agent can write the secure version. • (CC) Catalog coverage. CC is the share of later tasks whose vulnerability a principle addresses directly. II-D Results RQ1: Yes, agents reintroduce the same CWE after fixing it. In a new session, the agents introduced the same CWE at the later tasks in 26.7% of executions, averaged over both later tasks and all three distances from the fix, against 27.5% with no earlier fix (Table I ), a retention gain whose interval includes zero. The gain stays small for every agent, distance, and family (Table II ). A fix thus leaves almost no trace on later work, and an agent that has fixed a vulnerability is about as likely to write it again as one that never met it. RQ2: Recurrence is a failure of retention, not of capability. The agents fixed 85.7% of the vulnerabilities (Table I ), and while the fix stayed in context (same session), recurrence on a later task of the same family fell by about 20 points and stayed lower six tasks later (Table II ). The agents can therefore write the secure version and apply it to a later variant of the task when the fix remains in the conversation. However, the fix did not lower recurrence on another family of the same CWE, which suggests that what the agents keep is tied to the fixed task rather than to the CWE. RQ3: Persistent context helps only when the agent is asked, and only on the same family. With memory features enabled, no agent recorded the fix, and none of the 36 later sessions held a trace of it. When asked, the agents wrote a note in 28 of 36 cases, and the note lowered recurrence on the same family as much as keeping the fix in context did, but not on another family (Table II ). Nearly half of the notes (13 of 28) tie the lesson to the fixed task’s own functions or fields, and a verbatim record of the failed code and its fix was likewise tied to the fixed task’s family in the preliminary study (Appendix B ). Persistent context can carry a fix forward, but agents do not use it for that on their own, and what they write describes the task they fixed rather than a lesson for the CWE. RQ4: No. Published principles cover most of these vulnerabilities but do not prevent them. An OWASP principle directly addresses the vulnerability in 19 of the 27 later tasks (CC = 70%; a second rater agrees on 25 of the 27, Cohen’s , Appendix B ), yet neither all 218 principles nor only the relevant ones measurably lower recurrence (levels (b) and (c) in Table III ). The knowledge these tasks need is largely published, but in its general form it does not produce the checks that the code requires. Recurrence falls as the guidance becomes more specific. The same knowledge restated for the class of code (level (d)) lowers it by 10.8 points with little observed loss of working code, and guidance that states what the task’s code must check (level (e)) is about as effective as describing the reference fix (level (f)). Levels (e) and (f) serve only as reference points, however. Each must be written for a single task by someone who already knows its vulnerability, and it does not carry over to other tasks, so supplying such guidance to an agent across many tasks is impractical.
